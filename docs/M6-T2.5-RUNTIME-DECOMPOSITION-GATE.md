# M6-T2.5 运行时分解与可测试性架构门审查报告

**审查日期**: 2024 M6-T2.5  
**审查范围**: SpringAiToolCallingEngine 内部架构与测试可维护性  
**审查目标**: 判断是否需要有针对性的内部重构

## A. 执行诊断

### 结论

**当前复杂度处于架构债务早期信号阶段，但尚未跨越不可维护阈值。**

### 架构债务证据

1. **方法参数膨胀**: `reconstructAndExecuteApproved()` 达到 7 个参数
2. **派生参数重复**: processId、checkpointVersion 从 checkpoint 多次重复提取
3. **职责交织**: Engine 同时处理初始执行、暂停、恢复、协议重建、事件发射
4. **测试脆性开始显现**: M6 引入事件系统后构造成本增加

### 尚未到达危机的证据

1. **规模可控**: 1078 行对于核心引擎仍在可接受范围
2. **测试未大规模失败**: 虽有脆性信号但未崩溃
3. **公共 API 未受影响**: 客户端代码无感知
4. **核心语义边界清晰**: Checkpoint、Evidence、ExecutionLedger 权威边界稳定

### 不是正常增长的证据

- 新增能力（M6 事件）需要修改多个现有方法签名
- 事件上下文（processId/version/listener）作为可选参数在多层传递
- ProtocolReconstructor 逐渐承担执行职责而非纯协议重建

### 建议

**有针对性的内部重构，而非全面重写。**

## C. 变更扩散分析

### 能力 → Engine 方法变更矩阵

| 能力 | Engine 方法变更 | 其他类型变更 |
|------|----------------|-------------|
| **M5 持久恢复** | • `resumeProcess()` (新增)<br>• `durableContinueWithMessages()` (新增)<br>• `handleDurableReSuspension()` (新增)<br>• `suspendForApprovalDurable()` (新增)<br>• `loadAndValidateCheckpoint()` (新增)<br>• `resolveBinding()` (新增)<br>• `reconstructAndExecuteApproved()` (新增)<br>• `reconstructDenialResponses()` (新增)<br>• 构造函数修改（+3 参数） | CheckpointStore<br>RuntimeBindingResolver<br>ProtocolReconstructor<br>ProcessFactory |

| **M6 工具事件** | • `reconstructAndExecuteApproved()` (修改 - 添加事件参数+3) | EvidenceCapturingToolCallback<br>ProtocolReconstructor |

### 变更扩散模式识别

#### 模式 1：事件横切 🔴
- **现象**: M6 事件能力需要修改 4 个持久路径方法
- **机制**: 每个方法添加 `emitEvent()` 调用
- **构造变更**: 添加 `executionEventSink` 字段
- **缺失边界**: 没有专门的"持久执行协调器"拥有事件发射职责

#### 模式 2：参数穿透 🔴
- **现象**: processId、checkpointVersion、executionEventSink 作为可选上下文在多层传递
- **影响**: `reconstructAndExecuteApproved()` 7 参数中 3 个（processId, checkpointVersion, eventListener）仅用于事件
- **影响**: EvidenceCapturingToolCallback 构造接受 5 个参数（2 个核心 + 3 个事件上下文）

#### 模式 3：持久路径膨胀 🔴
- **现象**: 持久恢复引入 8 个新私有方法
- **影响**: `resumeProcess()` 成为 101 行编排方法
- **缺失抽象**: 没有明确的"持久恢复"聚合类型

### 结论

- ✅ 新能力不是通过修改单一方法实现（良好解耦）
- 🔴 新能力需要修改多个相关方法（缺少统一协调点）
- 🔴 横切关注点（事件）通过参数传递而非专有协调器

## D. 参数爆炸审计

### >= 5 参数的方法

#### 1. `reconstructAndExecuteApproved()` - 7 参数 🔴

**签名**:
```java
private List<Message> reconstructAndExecuteApproved(
    SuspensionCheckpoint checkpoint,              // A类
    RuntimeBinding binding,                       // A类
    List<Evidence> historicalEvidences,           // B类
    List<Evidence> newEvidences,                  // E类
    String processId,                             // C类 ⚠️
    Long checkpointVersion,                       // C类 ⚠️
    ExecutionEventListener eventListener)         // A类
```

**参数分类**:
- **A类（稳定对象依赖）**: checkpoint, binding, eventListener
- **B类（调用状态）**: historicalEvidences
- **C类（派生参数 ⚠️）**: processId, checkpointVersion - **已在 checkpoint 中存在**
- **E类（输出累加器）**: newEvidences

**问题**:
- processId 和 checkpointVersion 已被 checkpoint 拥有（`checkpoint.processId()`, `checkpoint.checkpointVersion()`）
- 重复传递创建"双重真相源"风险
- 增加签名复杂度

**修复建议**:
```java
// 应该是：
private List<Message> reconstructAndExecuteApproved(
    SuspensionCheckpoint checkpoint,     // processId/version 从这里获取
    RuntimeBinding binding,
    List<Evidence> historicalEvidences,
    List<Evidence> newEvidences,
    ExecutionEventListener eventListener)  // 5 参数
```

#### 2. `EvidenceCapturingToolCallback` 构造函数 - 5 参数 ⚠️

**签名**:
```java
EvidenceCapturingToolCallback(
    ToolCallback delegate,                        // A类
    List<Evidence> evidences,                     // E类
    String processId,                             // D类
    Long checkpointVersion,                       // D类
    ExecutionEventListener eventListener)         // D类
```

**参数分类**:
- **A类（稳定对象）**: delegate
- **E类（输出累加器）**: evidences
- **D类（可选特性管道）**: processId, checkpointVersion, eventListener - 三个参数全为事件上下文

**评估**:
- 5 参数处于可接受边界
- 事件上下文 3 参数有内聚性（都为事件服务）
- 可考虑 `EventEmissionContext` 记录类，但当前尚可接受

**建议**: 保持当前形式（除非未来添加更多事件参数）

### 其他方法

所有其他方法 <= 4 参数，在可接受范围内。

## E. 派生参数发现

### 违规实例

#### 实例 1: `reconstructAndExecuteApproved()` 参数重复 🔴

**当前调用**（在 `resumeProcess()` L746-750）:
```java
continuationMessages =
    reconstructAndExecuteApproved(
        checkpoint,                    // ✓ 权威
        binding,
        historicalEvidences,
        newEvidences,
        processId,                     // ⚠️ 派生自 checkpoint.processId()
```

**问题**:
1. checkpoint 已拥有 processId 和 checkpointVersion
2. 重复传递创建"双重真相源"风险
3. 如果调用方传递错误值，与 checkpoint 不一致

**修复**:
```java
// 应该是：
continuationMessages =
    reconstructAndExecuteApproved(
        checkpoint,           // processId/version 从这里获取
        binding,
        historicalEvidences,
        newEvidences,
        executionEventSink);
```

方法内部从 checkpoint 获取:
```java
String processId = checkpoint.processId();
Long checkpointVersion = checkpoint.checkpointVersion();
```

### 可接受的重复提取

#### `emitEvent()` 调用中的提取 ✅

**模式**（多处出现）:
```java
emitEvent(
    checkpoint.processId(),        // 每次调用都提取
    EventType.SUSPENDED,
    checkpoint.checkpointVersion(), // 每次调用都提取
```

**评估**: 这种重复**可以接受**
- `emitEvent()` 是通用辅助方法，不应耦合 Checkpoint 类型
- 调用点提取是明确的权威访问
- 不构成"派生参数"问题（没有跨方法重复传递同一权威）

## G. ProtocolReconstructor 职责评估

### 当前职责分析

#### ProtocolReconstructor 实际做什么

**方法 1: `executeApprovedBatch()`** (L76-136)
1. ✅ 协议重建：PendingToolCall → AssistantMessage.ToolCall (L87-95)
2. ✅ 协议重建：构建 ChatResponse (L97-105)
3. 🔴 执行关注点：用 EvidenceCapturingToolCallback 包装工具 (L109-120)
4. 🔴 执行关注点：通过 ToolCallingManager 执行工具 (L130)
5. ✅ 协议重建：返回 continuation messages (L135)

**方法 2: `constructDenialResponses()`** (L148-184)
1. ✅ 协议重建：构建 AssistantMessage (L152-161)
2. ✅ 协议重建：构建 ToolResponseMessage（拒绝）(L164-172)
3. ✅ 协议重建：返回 continuation messages (L175-182)

### 六个关键问题

#### Q1: 是否仅重建协议？
**答案：否。**

`executeApprovedBatch()` 同时承担：
- ✅ 协议重建（符合名称）
- 🔴 工具包装（执行关注点）
- 🔴 工具执行（执行关注点）
- 🔴 Evidence 收集（执行关注点，通过包装器）
- 🔴 事件发射（执行关注点，通过包装器）

#### Q2: 是否执行 ToolCallbacks？
**答案：是 - 通过 ToolCallingManager.executeToolCalls()。**

#### Q3: 是否捕获 Evidence？
**答案：间接捕获 - 通过 EvidenceCapturingToolCallback 包装器。**

#### Q4: 是否发射 ExecutionEvents？
**答案：间接发射 - 通过 EvidenceCapturingToolCallback（当提供事件上下文时）。**

#### Q5: 是否需要 process/checkpoint 信息？
**答案：是 - `executeApprovedBatch()` 接受 processId/checkpointVersion/eventListener。**

#### Q6: 是否已成为执行协调器而非重建器？
**答案：部分是。**

- `constructDenialResponses()` 是**纯协议重建** ✅
- `executeApprovedBatch()` 是**协议重建 + 工具执行协调** ⚠️

### 三个方向评估

#### 选项 A：保持当前职责 ⚠️ 可接受但名称部分误导

**理由**：
- 工具执行与协议重建在 Spring AI 机制中紧密耦合
- ToolCallingManager 需要重建的 ChatResponse 才能执行
- 分离可能创造人工边界

**缺点**：
- 类名"ProtocolReconstructor"不再完全准确
- 承担了超出"重建"的执行协调

#### 选项 B：收窄 ProtocolReconstructor ⚠️ 可能过度分解

**提议**：
- ProtocolReconstructor 仅构建协议消息
- 工具实际调用属于其他地方

**问题**：
- Spring AI 的 ToolCallingManager.executeToolCalls() 需要 ChatResponse 输入
- 协议重建和工具执行在技术上无法完全分离
- 可能创造不必要的传递层

#### 选项 C：重命名/泛化 ✅ 推荐（但延迟）

**提议**：
- 如果当前职责已真正演化为"持久批次执行协调器"，考虑重命名
- 但仅在职责稳定后，且名称确实严重误导时

**当前评估**：
- `executeApprovedBatch()` 方法名实际准确（"执行"而非"重建"）
- `ProtocolReconstructor` 类名部分误导，但不严重
- **建议暂不行动** - 等待更多用例验证当前职责边界

### 结论

**ProtocolReconstructor 当前状态：可接受但监控中**

- ✅ `constructDenialResponses()` 职责纯粹（纯协议重建）
- ⚠️ `executeApprovedBatch()` 承担执行职责但有合理技术原因（Spring AI 耦合）
- ⚠️ 类名部分误导，但未到必须重命名阈值
- **建议**：保持当前形式，在 V1 之后根据更多用例重新评估

## H. 工具调用边界评估

### 当前边界所有权

#### EvidenceCapturingToolCallback 拥有边界 ✅

**实现**（EvidenceCapturingToolCallback.java L98-131）：
```java
@Override
public String call(String functionArguments) {
    String toolName = delegate.getToolDefinition().name();
    
    String result;
    try {
        result = delegate.call(functionArguments);  // ← 调用边界
    } catch (Exception toolFailure) {
        emitToolFailedEvent(toolName);              // ← TOOL_FAILED 真相
        throw toolFailure;                          // 重新抛出
    }
    
    emitToolExecutedEvent(toolName);                // ← TOOL_EXECUTED 真相
    captureEvidence(toolName, result);              // ← Evidence 观察
    return result;
}
```

**边界清晰性评估**：✅ **边界清晰且正确定位**

1. ✅ 委托调用在 try 块内（唯一执行点）
2. ✅ TOOL_EXECUTED/FAILED 紧邻真相点
3. ✅ Evidence 捕获在成功路径
4. ✅ 事件发射失败不影响工具执行真相（防御性 catch）

### 长期所有权

**问题：哪个类型应长期拥有此边界？**

**答案：EvidenceCapturingToolCallback 是正确且稳定的所有者。**

**理由**：
1. 它是 ToolCallback 包装器 - 自然拦截点
2. 它已同时拥有 Evidence 和 Event 关注点
3. 工具观察不应分散到 Engine 方法中
4. 包装器模式允许灵活组合（未来可能有其他包装器）

**建议**：✅ **保持当前边界，不重构。**

#### ✅ Checkpoint = 恢复权威
- SuspensionCheckpoint 拥有 processId、version、pendingBatch、sessionId

- ExecutionLedger 分配 sequence、recordId、occurredAt
- ExecutionEvent 不包含这些字段

- **验证**：✅ 通过

- Evidence 由工具执行创建
- EvidenceCapturingToolCallback 是唯一创建点

- **验证**：✅ 通过

- Engine 通过 ChatMemory 接口读写
- 不绕过 ChatMemory 直接操作消息
- **验证**：✅ 通过

#### ✅ ExecutionEvent = 已真实事实通知
- 事件在领域转换成功后发射
- Listener 失败不回滚领域事实
- **验证**：✅ 通过

### 重构必须保持的不变式

1. Checkpoint 仍是恢复权威
2. ExecutionLedger 仍分配 sequence
3. Evidence 仍由工具执行产生
4. ExecutionEvent 仍在事实之后发射
5. Listener 失败仍不影响执行真相

**结论**：✅ **当前权威边界清晰且稳定，重构风险低。**

## U. M5/M6 不变式审查

### 必须保持的语义

#### ✅ M5 持久语义

1. **CHECK A 前置验证**
   - checkpoint 存在性检查
   - 版本匹配验证（栅栏令牌）
   - CHECK A 失败 = 零工具副作用

2. **CHECK B CAS 转换**
   - 完成：deleteIfVersion
   - 重新暂停：replaceIfVersion
   - 失败抛出 CheckpointTransitionConflictException

3. **RuntimeBinding 解析**
   - 从 checkpoint 恢复 definition + context
   - 绑定解析失败抛出 ResumePreparationException

4. **协议重建**
   - PendingToolCall → AssistantMessage.ToolCall
   - 保留原始 toolCallId
   - Spring AI ToolCallingManager 执行

5. **Evidence 累积**
   - 历史 Evidence 从 checkpoint 恢复
   - 新 Evidence 从恢复执行收集
   - 最终合并返回

6. **ChatMemory 语义**
   - 恢复：从 sessionId 读取历史
   - 完成：手动持久化最终 Assistant 消息

#### ✅ M6 事件语义

1. **事件因果顺序**
   - 领域转换成功 → 发射事件
   - 事件不创建真相，只通知

2. **生命周期事件**
   - APPROVAL_REQUIRED（治理决策）
   - SUSPENDED（checkpoint 创建成功）
   - APPROVAL_GRANTED/REJECTED（CHECK A 后）
   - RESUMED（CHECK A + binding 解析后）
   - CHECKPOINT_CONFLICT（CHECK B 失败）
   - COMPLETED（CHECK B 删除成功）

3. **工具事件**
   - TOOL_EXECUTED（delegate 返回成功）
   - TOOL_FAILED（delegate 抛出异常）
   - 仅在持久批准恢复时发射（有 processId）

4. **投影失败隔离**
   - Listener 失败不回滚领域事实
   - CompositeExecutionEventListener 隔离失败
