## D. MISSING DURABLE FACT

### The Fact

**Missing Recovery-Critical Fact**:
```
INVOCATION_INTENT(processId, checkpointVersion, operationId) EXISTS
```

**Semantic Meaning**:
> A specific logical durable tool operation has crossed a durable execution gate after which physical invocation is permitted and MAY occur.

### What It Does NOT Mean

- ❌ Delegate definitely entered
- ❌ External request definitely sent  
- ❌ External side effect committed
- ❌ Tool completed successfully
- ❌ Tool failed
- ❌ Exactly one attempt will occur

### Correct Interpretation

**Before INVOCATION_INTENT persisted**:
- Physical invocation MUST NOT proceed
- Crash → operation is PENDING (not uncertain)
- Safe to replay

**After INVOCATION_INTENT persisted**:
- Physical invocation MAY proceed
- Crash → operation is UNCERTAIN (may have invoked)
- NOT safe to blindly replay

**After delegate.call() returns/throws**:
- TOOL_EXECUTED or TOOL_FAILED is true
- External outcome still UNKNOWN
- External cooperation required for effectively-once

## E. INVOCATION UNCERTAINTY vs EXTERNAL OUTCOME UNCERTAINTY

### Corrected Terminology

M6-T4 collapsed two distinct uncertainties. Separate them:

### Invocation Uncertainty

**Definition**: Arctra cannot determine whether a physical invocation actually entered/executed after durable intent was recorded.

**Conditions**:
1. INVOCATION_INTENT durably persisted
2. No TOOL_EXECUTED or TOOL_FAILED observation
3. Crash or system boundary crossed

**Example Timeline**:
```
T8: INVOCATION_INTENT persisted
T9: delegate.call() begins
T10: CRASH
Recovery: No TOOL_EXECUTED/FAILED evidence
Status: INVOCATION UNCERTAIN (may have entered delegate, may not have)
```

**Recovery Implication**: Cannot distinguish "never started" from "started but no outcome observed"

### External Outcome Uncertainty

**Definition**: Arctra knows invocation occurred or returned/threw, but cannot determine external commit/business outcome.

**Conditions**:
1. TOOL_EXECUTED or TOOL_FAILED observed
2. External system commit state UNKNOWN
3. Delegate threw timeout, network error, or ambiguous exception

**Example Timeline**:
```
T9: delegate.call() begins
T10: External HTTP request sent
T11: Network timeout
T12: delegate throws TimeoutException
T13: TOOL_FAILED emitted
Status: INVOCATION OBSERVED (delegate threw), EXTERNAL OUTCOME UNCERTAIN (transaction may have committed)
```

**Recovery Implication**: Need external query/receipt to determine actual commit

### Distinction

| Dimension | Invocation Uncertainty | External Outcome Uncertainty |
|-----------|------------------------|------------------------------|
| **Authority** | Arctra framework | External system |
| **Evidence needed** | INVOCATION_INTENT + no TOOL_EXECUTED/FAILED | TOOL_EXECUTED/FAILED + external receipt |
| **T4A scope** | ✅ YES | ❌ NO (defer) |
| **Requires** | Durable pre-call fact | External cooperation API |

**T4A Mission**: Solve **Invocation Uncertainty Detection** only.

## F. CORRECTED UNCERTAINTY DEFINITIONS

### Invocation Uncertainty (Precise Definition)

**An operation is INVOCATION-UNCERTAIN if and only if ALL of the following are true**:

1. `INVOCATION_INTENT(processId, checkpointVersion, operationId)` durably persists
2. No authoritative `TOOL_EXECUTED(operationId)` evidence exists
3. No authoritative `TOOL_FAILED(operationId)` evidence exists
4. System boundary crossed (crash, restart, or recovery scenario)

**NOT uncertain**:
- Ordinary `PENDING` without INVOCATION_INTENT (safe to execute)
- `TOOL_EXECUTED` observed (invocation completed, external outcome separate concern)
- `TOOL_FAILED` observed (invocation completed with exception, external outcome separate concern)

### External Outcome Uncertainty (Precise Definition)

**An operation has EXTERNAL-OUTCOME-UNCERTAINTY if and only if ALL of the following are true**:

1. `TOOL_EXECUTED(operationId)` OR `TOOL_FAILED(operationId)` observed (invocation completed)
2. Delegate result/exception is ambiguous (timeout, network error, non-authoritative failure)
3. No external receipt or authoritative commit evidence exists
4. External system MAY have committed business side effect

**NOT uncertain**:
- Delegate returned idempotent read operation result (no side effect)
- Delegate returned with external transaction rollback proof
- External system provides authoritative receipt (T4C scope)

### Why Separation Matters

**Invocation Uncertainty** → Arctra internal recovery decision (retry? query external? operator intervention?)  
**External Outcome Uncertainty** → External cooperation required (receipt API, idempotency key, query endpoint)

**T4A addresses ONLY Invocation Uncertainty foundation**.

### Authority Analysis

**Question 1**: What exact fact would Checkpoint now own that it does not own today?

**Answer**: Physical execution window state: whether a logical pending operation has crossed the durable gate permitting physical invocation.

**Question 2**: Is invocation state genuinely part of resumable process state?

**Answer**: NO. Resumable process state is "what work remains to be done" (pending operations, accumulated evidence, conversation session). Invocation state is "what physical execution attempts may have occurred" (recovery window tracking).

**Question 3**: Does this expand Checkpoint responsibility coherently or overload it?

**Answer**: OVERLOAD. Checkpoint currently owns suspension points (where execution CAN resume). Adding invocation state makes it own execution windows (where uncertainty exists). These are separate concerns.

**Question 4**: Does PendingToolCall become both logical pending operation description AND physical invocation recovery state?

**Answer**: YES. This violates single responsibility.

**Question 5**: Is that responsibility combination acceptable?

**Answer**: NO. Logical operation identity (what to execute) should remain separate from physical execution tracking (what may have executed).

**Question 6-8**: Does checkpoint schema need to change? Does schemaVersion change? Does arctra-core change?

**Answer**: YES to all. Adding `InvocationState` or equivalent to PendingToolCall or SuspensionCheckpoint changes the schema. Schema version would increment from "1.1" to "1.2". Since PendingToolCall and SuspensionCheckpoint are in `arctra-core`, core MUST change.

**Question 9**: Can public API delta really remain zero if PendingToolCall changes?

**Answer**: NO. PendingToolCall is a public record in `cn.bitcss.arctra.checkpoint` package. Any constructor/field change is a public API change, even if only runtime-internal code uses the new field.

**Question 10-11**: Does writing intent require replaceIfVersion()? Does checkpointVersion increment?

**Answer**: YES. To durably record invocation intent, must write new checkpoint state. Current CheckpointStore only provides `replaceIfVersion(processId, expectedVersion, replacement)`. Recording intent = new checkpoint version.

**Question 12**: Does current CHECK B still operate against the original version?

**Answer**: NO. If intent recording increments version from v1 → v2, then CHECK B must use v2, not v1.

**Question 13**: Must CHECK B be redesigned?

**Answer**: YES. Current CHECK B uses the version from the checkpoint loaded at CHECK A. If intent recording creates intermediate versions, CHECK B logic must track "current expected version" not "original loaded version".

**Question 14**: Does an intent write become a new CHECK between A and B?

**Answer**: YES. Semantically it becomes "CHECK A½": validate still-current, record intent, proceed.

**Question 15-17**: Who owns this transition? Is DurableResumeCoordinator forced to participate? Does ProtocolReconstructor still own physical execution?

**Answer**: Unclear responsibility boundary. If checkpoint owns intent, does Coordinator write it (expanding Coordinator into execution gating)? Or does ProtocolReconstructor write it (giving execution layer checkpoint write access)?

**Question 18**: Where exactly is the durable gate relative to delegate.call()?

**Answer**: Must be immediately before delegate.call() in ProtocolReconstructor, but checkpoint write is a Coordinator-level concern. This creates layering tension.

## H. CANDIDATE A — CONCURRENCY TIMELINE

### Current Concurrent Resume Behavior (Frozen)

**Timeline**:
```
Worker A: CHECK A (v1) → execute op-A → CHECK B (v1 → delete)
Worker B: CHECK A (v1) → execute op-A → CHECK B (v1 → delete)

T0: Both workers load checkpoint v1
T1: A validates v1 (success)
T2: B validates v1 (success)  
T3: A executes op-A (physical invocation #1)
T4: B executes op-A (physical invocation #2)
T5: A attempts deleteIfVersion(v1) → SUCCESS
T6: B attempts deleteIfVersion(v1) → CONFLICT (checkpoint already deleted)
```

**Result**: Both workers execute op-A. One CHECK B wins (A), one conflicts (B). This is intentional **at-least-once** behavior.

### Candidate A with CAS Intent Recording

**Timeline with CAS**:
```
Worker A: CHECK A (v1) → CAS intent (v1→v2) → execute → CHECK B (v2→delete)
Worker B: CHECK A (v1) → CAS intent (v1→v2) → execute → CHECK B (v2→delete)

T0: Both workers load checkpoint v1
T1: A validates v1 (success)
T2: B validates v1 (success)
T3: A attempts replaceIfVersion(v1, checkpoint_v2_with_intent) → SUCCESS
T4: B attempts replaceIfVersion(v1, checkpoint_v2_with_intent) → CONFLICT (current version is v2)
T5: A proceeds to execute op-A (physical invocation #1)
T6: B's CAS failed → what happens?
```

**Critical Question**: After B's CAS fails at T4, can B still execute op-A?

**Option 1**: B CANNOT execute (CAS failure blocks execution)
- **Implication**: Candidate A has introduced **operation claiming**
- **Semantic change**: Single-worker execution semantics (first CAS winner executes)
- **At-least-once behavior**: CHANGED (now at-most-once per attempt)
- **Lease/fencing pressure**: INTRODUCED (need timeout for claim expiry)

**Option 2**: B CAN execute (CAS failure is advisory)
- **Implication**: Both workers still execute
- **Question**: What is checkpoint state authority?
  - If A wrote v2 with intent, checkpoint says "A claimed"
  - If B executes anyway, checkpoint authority is violated
- **Inconsistency**: Checkpoint says "intent from A" but B also invoked

### Candidate A without CAS (Non-Versioned Intent Write)

**Could checkpoint intent be written WITHOUT using version/CAS?**

**Answer**: Technically yes, but then:
1. **Checkpoint authority coherence LOST**: If checkpoint transitions don't use CAS, concurrent writes can corrupt state
2. **CHECK B safety LOST**: Current CHECK B depends on version-based conflict detection
3. **InMemoryCheckpointStore contract VIOLATED**: Current API only provides CAS operations

### Concurrency Verdict

**Candidate A forces a choice**:
- Use CAS → Introduces claiming/single-worker semantics (semantic change)
- Don't use CAS → Violates checkpoint authority coherence (architectural damage)

**Both outcomes are unacceptable for T4A**.

**Option 1**: Checkpoint only tracks INTENT (not outcome)
- Recovery sees: INTENT + no outcome → UNCERTAIN

- **Problem**: Checkpoint becomes execution state machine (scope creep)

- NOT a tool failure (delegate never called)
- NOT a governance failure
- Framework infrastructure failure (storage unavailable, disk full, network partition)

**Recovery Strategy**: Infrastructure repair, then retry resume.
