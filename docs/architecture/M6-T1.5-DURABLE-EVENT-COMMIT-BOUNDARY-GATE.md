## A. 源代码真相 — M5执行时间线

### A1. 初始执行 → 首次暂停（APPROVAL_REQUIRED）

**时间线（从SpringAiToolCallingEngine.execute()）:**

```
1. 创建evidence收集器（Collections.synchronizedList）
2. 包装tools为EvidenceCapturingToolCallback
3. 包装tools为GovernanceToolCallingAdvisor
4. 构建ChatClient.prompt()
5. 添加GovernanceToolCallingAdvisor
6. 调用promptSpec.call()
   ↓
7. 模型返回AssistantMessage(toolCalls=[...])
   ↓
8. GovernanceToolCallingAdvisor拦截
9. 对每个toolCall评估governance policy
10. 发现需要approval → 抛出ToolApprovalRequiredSignal
    ↓
11. catch ToolApprovalRequiredSignal
12. isDurableMode() ? suspendForApprovalDurable : suspendForApprovalEphemeral
    ↓
13. suspendForApprovalDurable():
    a. 生成processId = "P-" + UUID
    b. 提取pendingBatch (List<PendingToolCall>)
    c. 构建SuspensionCheckpoint(
         schemaVersion="1.0"
         processId
         checkpointVersion=1
         runtimeBindingKey
         sessionId
         pendingBatch
         accumulatedEvidences=List.copyOf(evidences)  ← 此时evidences通常为空
       )
    d. checkpointStore.create(checkpoint)  ← DURABLE COMMIT POINT
    e. ProcessFactory.createDurableSuspended(processId, 1L, this)
    f. return new AgentResult(partialContent, evidences, process)
```

**关键观察:**
- **APPROVAL_REQUIRED的事实在步骤9成立** — governance decision返回REQUIRE_APPROVAL
- **SUSPENDED的事实在步骤13.d成立** — checkpoint.create()成功后
- **此时无工具执行**，evidences列表为空
- **checkpoint.create()是唯一durable commit point**

### A2. 批准恢复 → 完成（APPROVED → RESUMED → TOOL_EXECUTED → COMPLETED）

**时间线（从SpringAiToolCallingEngine.resumeProcess()）:**

```
1. 入参: processId, checkpointVersion, ContinuationSignal.approved()
   ↓
2. CHECK A:
   a. checkpoint = checkpointStore.load(processId)
   b. if (checkpoint.checkpointVersion != expectedVersion)
      → throw StaleCheckpointException
   ↓
3. RuntimeBinding resolution:
   binding = bindingResolver.resolve(processId, runtimeBindingKey, sessionId)
   如果失败 → throw ResumePreparationException
   ↓
4. 识别signal类型:
   if (signal instanceof ApprovalSignal approval)
     if (approval.approved())
       → resumeApprovedExecution(checkpoint, binding, ...)
     else
       → resumeRejectedExecution(checkpoint, binding, ...)
   ↓
5. resumeApprovedExecution():
   a. 合并historical evidences = checkpoint.accumulatedEvidences
   b. 创建new evidences收集器
   c. reconstructAndExecuteApproved(checkpoint, binding, historical, new)
      ↓
      i. 获取conversationHistory from ChatMemory
      ii. ProtocolReconstructor.executeApprovedBatch(pendingBatch, ...)
          → 重建AssistantMessage(toolCalls)
          → toolCallingManager.executeToolCalls()  ← TOOLS EXECUTE HERE
          → 工具回调执行，副作用发生
          → 结果包装为ToolResponseMessage
          → evidences通过EvidenceCapturingToolCallback收集
      iii. 返回messages = [history + AssistantMessage + ToolResponseMessage]
   d. mergedEvidences = historical + new
   e. 使用messages继续模型调用（governanceAdvisor仍active）
   f. content = promptSpec.call().content()
      → 可能返回最终答案
      → 或抛出新的ToolApprovalRequiredSignal（re-suspension）
   ↓
6. 假设完成路径（无re-suspension）:
   g. CHECK B DELETE:
      deleted = checkpointStore.deleteIfVersion(processId, checkpointVersion)
      if (!deleted) → throw CheckpointTransitionConflictException
   h. persistCompletedAssistant(context, content)
      → chatMemory.add(assistantMessage)
   i. return new AgentResult(content, mergedEvidences)
```

**关键观察:**
- **APPROVAL_GRANTED的事实** — 在步骤1明确（signal是APPROVED）
- **RESUMED的事实** — 在步骤2（CHECK A通过）或步骤3（binding resolved）或步骤5.c.ii（工具开始执行）？需要选择
- **TOOL_EXECUTED的事实** — 在步骤5.c.ii工具回调返回成功时
- **COMPLETED的事实** — 在步骤6.g（CHECK B成功）或步骤6.h（ChatMemory写入成功）或步骤6.i（返回结果）？需要选择
- **工具副作用在CHECK B之前已经发生**
- **存在crash window:** CHECK B成功 → ChatMemory写入失败

### A3. 拒绝恢复 → 完成（REJECTED → COMPLETED）

**时间线（从resumeRejectedExecution()）:**

```
1. CHECK A通过，binding resolved（同上）
   ↓
2. reconstructAndRejectApproved():
   a. 重建AssistantMessage(toolCalls)
   b. 构建denial ToolResponseMessage(所有tool返回"rejected")
   c. 返回messages = [history + AssistantMessage + denial ToolResponseMessage]
   ↓
3. 使用messages调用模型（无governance advisor）
   content = promptSpec.call().content()
   ↓
4. CHECK B DELETE:
   deleted = checkpointStore.deleteIfVersion(processId, checkpointVersion)
   if (!deleted) → throw CheckpointTransitionConflictException
   ↓
5. persistCompletedAssistant(context, content)
   ↓
6. return new AgentResult(content, evidences)
```

**关键观察:**
- **APPROVAL_REJECTED的事实** — 在signal是REJECTED时成立
- **无真实工具执行**，只有模拟rejection响应
- **COMPLETED的事实** — 同样在CHECK B或ChatMemory写入成功时

### A4. 批准恢复 → 重新暂停（RE-SUSPENSION）

**时间线（从resumeApprovedExecution() catch分支）:**

```
1-5.c.ii. 工具执行完成，evidences收集
   ↓
5.e. 模型continuation调用
5.f. promptSpec.call().content()
     → 模型返回新的AssistantMessage(toolCalls=[...])
     → GovernanceToolCallingAdvisor拦截
     → 新的governance decision = REQUIRE_APPROVAL
     → 抛出ToolApprovalRequiredSignal
   ↓
catch ToolApprovalRequiredSignal:
   handleDurableReSuspension(oldCheckpoint, signal.state(), mergedEvidences, ...)
   ↓
a. 提取nextPendingBatch from new toolCalls
b. 构建newCheckpoint(
     schemaVersion="1.0"
     processId=old.processId  ← 保持不变
     checkpointVersion=old.checkpointVersion + 1  ← 递增
     runtimeBindingKey
     sessionId
     pendingBatch=nextPendingBatch
     accumulatedEvidences=mergedEvidences  ← 包含之前执行的工具证据
   )
c. CHECK B REPLACE:
   replaced = checkpointStore.replaceIfVersion(
       processId,
       old.checkpointVersion,
       newCheckpoint
   )
   if (!replaced) → throw CheckpointTransitionConflictException
d. ProcessFactory.createDurableSuspended(processId, newCheckpoint.checkpointVersion, this)
e. return new AgentResult(partialContent, mergedEvidences, process)
```

**关键观察:**
- **新的APPROVAL_REQUIRED** — 在governance decision时成立
- **SUSPENDED(v+1)** — 在步骤c CHECK B REPLACE成功后
- **工具执行已经发生**，副作用不可撤销
- **checkpoint version递增** (1 → 2 → 3 ...)
- **accumulatedEvidences单调累积**

### A5. 并发冲突（CHECK B LOSER）

**场景:** Runtime A和Runtime B都通过CHECK A，都执行工具，但只有一个赢得CHECK B

**Runtime A时间线:**
```
CHECK A通过 (v3)
工具执行 → 副作用发生
evidences收集
模型调用
CHECK B deleteIfVersion(v3) → TRUE ✅
persistCompletedAssistant
return success
```

**Runtime B时间线（同时）:**
```
CHECK A通过 (v3)
工具执行 → 副作用发生  ← DUPLICATE EXECUTION
evidences收集
模型调用
CHECK B deleteIfVersion(v3) → FALSE ❌  ← A已经删除了
throw CheckpointTransitionConflictException
```

**关键观察:**
- **TOOL_EXECUTED对于B是TRUE** — 工具确实执行了
- **CHECKPOINT_CONFLICT对于B是TRUE** — CHECK B失败
- **B的工具副作用已经发生**，无法撤销
- **B的历史必须保留**，不能假装工具没执行
- **M5提供at-least-once语义**，不是exactly-once

---

### A6. ResumePreparationException

**时间线:**
```
CHECK A通过
binding = bindingResolver.resolve(processId, runtimeBindingKey, sessionId)
→ throw exception (resolver失败)
  ↓
catch ResumePreparationException
→ 包装并抛出到caller
```

**关键观察:**
- **RESUMED不成立** — 绑定解析失败
- **checkpoint仍然存在** — 可以重试
- **无副作用发生** — 工具未执行

## B. 事件提交边界表

### B1. PROCESS_STARTED

| 维度 | 值 |
|------|------|
| **语义事实** | Agent进程身份建立，执行开始 |
| **精确提交点** | processId分配后（ephemeral: function materialized; durable: processId生成） |
| **相对checkpoint操作** | BEFORE（初始暂停前）或N/A（ephemeral完成） |
| **相对工具副作用** | BEFORE |
| **相对ChatMemory写入** | BEFORE（初始UserMessage已写入） |
| **CHECK B失败后仍TRUE?** | YES — 进程确实启动过 |
| **审计关键?** | Medium — 用于追踪进程创建 |
| **恢复关键?** | NO |
| **Ledger append失败应阻止执行?** | NO — 进程创建不依赖ledger |
| **最小payload** | `{"requestId": "...", "sessionId": "...", "durableMode": true/false}` |

**语义评估:** ⚠️ **PROVISIONAL** — "started"语义模糊  
**推荐:** 当前可用，但未来可能细化为PROCESS_CREATED vs EXECUTION_STARTED

---

### B2. APPROVAL_REQUIRED

| 维度 | 值 |
|------|------|
| **语义事实** | Governance policy评估决定需要human approval |
| **精确提交点** | GovernanceDecision返回REQUIRE_APPROVAL时 |
| **相对checkpoint操作** | BEFORE checkpoint.create() |
| **相对工具副作用** | BEFORE — 工具未执行 |
| **相对ChatMemory写入** | AFTER AssistantMessage(toolCalls)已追加 |
| **CHECK B失败后仍TRUE?** | YES — governance决策确实发生 |
| **审计关键?** | HIGH — 治理决策审计 |
| **恢复关键?** | NO |
| **Ledger append失败应阻止执行?** | NO — 但应该记录失败本身 |
| **最小payload** | `{"toolNames": [...], "policyReason": "...", "checkpointVersion": 1}` |

**语义评估:** ✅ **PRECISE** — 对应明确的governance decision  
**推荐:** 可以安全wiring

---

### B3. SUSPENDED

| 维度 | 值 |
|------|------|
| **语义事实** | Durable checkpoint成功创建，进程进入WAITING状态 |
| **精确提交点** | checkpointStore.create() 或 replaceIfVersion() 返回成功 |
| **相对checkpoint操作** | IMMEDIATELY AFTER checkpoint commit |
| **相对工具副作用** | 初始暂停: BEFORE; 重新暂停: AFTER |
| **相对ChatMemory写入** | AFTER conversation已持久化 |
| **CHECK B失败后仍TRUE?** | 初始暂停: N/A; 重新暂停: NO（如果replaceIfVersion失败，新checkpoint不存在） |
| **审计关键?** | HIGH — 暂停点审计 |
| **恢复关键?** | YES — 标记可恢复状态 |
| **Ledger append失败应阻止执行?** | ⚠️ Debatable — checkpoint已存在，append失败不影响恢复 |
| **最小payload** | `{"checkpointVersion": N, "pendingToolCount": M, "evidenceCount": K}` |

**语义评估:** ✅ **PRECISE** — 对应checkpoint durable commit  
**推荐:** 可以安全wiring，但需要处理append失败后checkpoint仍有效的情况

**关键设计问题:**
```
checkpoint.create() succeeds
ledger.append(SUSPENDED) fails
```
**结果:** Checkpoint存在（可恢复），但ledger无SUSPENDED记录（审计不完整）

**推荐策略:** SUSPENDED append失败不应阻止返回suspended AgentResult，但应该:
1. 记录append失败到logs
2. 允许后续reconciliation scanner补录
3. 或者使用outbox pattern保证最终一致性

---

### B4. APPROVAL_GRANTED

| 维度 | 值 |
|------|------|
| **语义事实** | Human批准了pending tool batch execution |
| **精确提交点** | resumeProcess(signal=APPROVED)被调用 |
| **相对checkpoint操作** | AFTER CHECK A (checkpoint.load()成功) |
| **相对工具副作用** | BEFORE — 工具尚未执行 |
| **相对ChatMemory写入** | BEFORE — 工具执行后才写入ToolResponseMessage |
| **CHECK B失败后仍TRUE?** | YES — 批准决策确实发生，即使后续CHECK B失败 |
| **审计关键?** | HIGH — 治理决策审计，合规要求 |
| **恢复关键?** | NO — 不影响恢复，只是审计trail |
| **Ledger append失败应阻止执行?** | ⚠️ HIGH RISK — 如果合规要求必须审计批准决策，append失败可能需要阻止 |
| **最小payload** | `{"checkpointVersion": N, "approver": "...", "approvedAt": "...", "toolNames": [...]}` |

**语义评估:** ✅ **PRECISE** — 对应明确的approval signal  
**推荐:** 可以安全wiring，但**审计关键性高**

**关键设计问题 (CRITICAL):**
```
resumeProcess(APPROVED) called
ledger.append(APPROVAL_GRANTED) fails
tool execution proceeds
```
**风险:** 合规审计缺失 — 工具执行了但无批准记录

**推荐策略:** 
- **Option A (Strict):** APPROVAL_GRANTED append失败 → 抛出异常，阻止工具执行
- **Option B (Relaxed):** 允许继续，但记录audit-append-failure到logs + 告警
- **取决于合规要求** — 金融/医疗系统可能需要Option A

| 维度 | 值 |
|------|------|
| **语义事实** | Human拒绝了pending tool batch execution |
| **精确提交点** | resumeProcess(signal=REJECTED)被调用 |
| **相对checkpoint操作** | AFTER CHECK A |
| **相对工具副作用** | N/A — 无真实工具执行 |
| **相对ChatMemory写入** | BEFORE — rejection ToolResponseMessage |
| **CHECK B失败后仍TRUE?** | YES — 拒绝决策确实发生 |
| **审计关键?** | HIGH — 治理决策审计 |

| **Ledger append失败应阻止执行?** | MEDIUM — 同APPROVAL_GRANTED |
| **最小payload** | `{"checkpointVersion": N, "rejector": "...", "rejectedAt": "...", "toolNames": [...]}` |

**语义评估:** ✅ **PRECISE**  
**推荐:** 可以安全wiring，审计关键性与APPROVAL_GRANTED相同

### B6. RESUMED

| 维度 | 值 |
|------|------|
| **语义事实** | ❓ **语义模糊 — 需要明确定义** |
| **候选边界** | A. resumeProcess()被调用<br/>B. CHECK A通过<br/>C. RuntimeBinding resolved<br/>D. 工具执行开始<br/>E. 工具执行完成 |

**语义分析:**

**Option A: resumeProcess() invoked**
- ❌ 过早 — 可能CHECK A失败

**Option B: CHECK A passed** ✅ **推荐**
- ✅ "成功从有效checkpoint开始恢复过程"
- 此时checkpoint已验证有效
- 但RuntimeBinding可能失败

**Option C: RuntimeBinding resolved**
- ✅ 也合理 — "成功准备好恢复执行"
- 但如果工具立即失败，仍然算RESUMED吗?

**Option D: First tool begins execution**
- ❌ 太晚 — 重要恢复阶段已经发生

**Option E: Tools completed**
- ❌ 太晚 — 这应该是另一个event

**推荐定义:**

```
RESUMED = "Durable process successfully began continuation from a valid checkpoint"
```

**精确提交点:** CHECK A通过 (checkpoint.load()成功 AND version匹配)

| 维度 | 值（基于Option B） |
|------|------|
| **语义事实** | 进程成功从有效checkpoint开始恢复 |
| **精确提交点** | CHECK A通过后 |
| **相对checkpoint操作** | IMMEDIATELY AFTER CHECK A |
| **相对工具副作用** | BEFORE |
| **相对ChatMemory写入** | AFTER — conversation history已加载 |
| **CHECK B失败后仍TRUE?** | YES — 恢复确实启动，虽然后续CHECK B失败 |
| **审计关键?** | MEDIUM — 恢复追踪 |
| **恢复关键?** | NO — 已经在恢复中了 |
| **Ledger append失败应阻止执行?** | NO |
| **最小payload** | `{"checkpointVersion": N, "runtimeBindingKey": "...", "signalType": "APPROVED/REJECTED"}` |

**语义评估:** ⚠️ **需要明确冻结语义** — 当前M6-T1 Javadoc说"Checkpoint loaded and CHECK A validation passed"  
**推荐:** 保持此定义，wiring到CHECK A通过后

### B7. TOOL_EXECUTED

| 维度 | 值 |
|------|------|
| **语义事实** | Framework观察到工具回调执行返回成功 |
| **精确提交点** | ToolCallback.execute()返回（无异常） |
| **相对checkpoint操作** | BEFORE CHECK B（工具先执行，CHECK B后验证） |
| **相对工具副作用** | IMMEDIATELY AFTER — 副作用已发生 |
| **相对ChatMemory写入** | BEFORE — ToolResponseMessage在工具执行后写入 |
| **CHECK B失败后仍TRUE?** | ✅ **YES (CRITICAL)** — 副作用不可撤销 |
| **审计关键?** | HIGH — 工具执行审计，尤其高风险工具 |
| **恢复关键?** | MEDIUM — 用于验证工具是否真的执行了 |
| **Ledger append失败应阻止执行?** | ⚠️ **CANNOT BLOCK** — 工具已执行，抛异常不撤销副作用 |
| **最小payload** | `{"toolCallId": "...", "toolName": "...", "evidenceId": "E42"}` |

**语义评估:** ⚠️ **PROVISIONAL** — 当前不区分:
- 本地callback返回 vs 外部操作确认
- 成功 vs uncertain outcome
- 幂等 vs 非幂等

**关键语义限制 (当前M6-T1):**
```
TOOL_EXECUTED means:
"The framework-observed tool callback execution returned successfully."

DOES NOT mean:
- External side effect is transactionally committed
- External system executed exactly once
- Operation receipt has been verified
```

**推荐:** 保持当前provisional语义，但:
1. Javadoc必须明确说明限制
2. 未来通过operationId/external receipts细化
3. Append失败只能记录到logs，不能阻止后续执行

**关键设计问题 (CRITICAL):**
```
tool callback executes → external side effect occurs
ledger.append(TOOL_EXECUTED) fails
what should happen?
```

**答案:** 
- ❌ **不能抛异常阻止执行** — 副作用已发生，无法撤销
- ✅ **必须继续执行** — 让进程完成或暂停
- ✅ **记录append失败到logs + 告警** — 审计不完整
- ✅ **未来reconciliation** — 扫描Evidence vs ExecutionRecord不一致

---

### B8. TOOL_FAILED

| 维度 | 值 |
|------|------|
| **语义事实** | Framework观察到工具回调执行失败（抛异常或返回错误） |
| **精确提交点** | ToolCallback.execute()抛出异常 |
| **相对checkpoint操作** | BEFORE CHECK B（或导致CHECK B不执行） |
| **相对工具副作用** | ❓ **不确定** — callback抛异常不代表外部副作用未发生 |
| **相对ChatMemory写入** | BEFORE — 失败可能不写入ToolResponseMessage或写入error |
| **CHECK B失败后仍TRUE?** | YES — 工具确实失败了 |
| **审计关键?** | HIGH — 失败审计，问题诊断 |
| **恢复关键?** | MEDIUM — retry决策依据 |
| **Ledger append失败应阻止执行?** | NO — 失败已经发生 |
| **最小payload** | `{"toolCallId": "...", "toolName": "...", "errorType": "...", "errorMessage": "..."}` |

**语义评估:** ⚠️ **PROVISIONAL & POTENTIALLY UNSAFE**

**关键语义陷阱:**
```
TOOL_FAILED currently means:
"The framework-observed tool callback threw an exception."

DANGEROUS assumption:
callback threw → external side effect did not occur

Reality:
tool sends HTTP request to remote server
remote server processes request
network timeout before response
→ callback throws TimeoutException
→ but remote side effect MAY have occurred
```

**推荐:** 
1. **保持provisional语义**，但Javadoc明确说明不确定性
2. **未来引入UNCERTAIN_OUTCOME** — 明确区分确定失败 vs 不确定结果
3. **当前wiring可用**，但不声称外部副作用未发生

### B9. CHECKPOINT_CONFLICT

| 维度 | 值 |
|------|------|
| **语义事实** | CHECK B条件更新失败（replaceIfVersion或deleteIfVersion返回false） |
| **精确提交点** | checkpointStore.replaceIfVersion()或deleteIfVersion()返回false |
| **相对checkpoint操作** | AFTER CHECK B失败 |
| **相对工具副作用** | AFTER — 工具已执行（at-least-once冲突） |
| **相对ChatMemory写入** | 失败前可能已部分写入 |
| **CHECK B失败后仍TRUE?** | N/A — 这本身就是CHECK B失败事件 |
| **审计关键?** | HIGH — 并发冲突审计 |
| **恢复关键?** | NO — 表示此执行失败，但不影响winner恢复 |
| **Ledger append失败应阻止执行?** | NO — CHECK B已失败，进程已终止 |
| **最小payload** | `{"checkpointVersion": N, "operation": "DELETE/REPLACE", "conflictType": "VERSION_MISMATCH"}` |

**语义评估:** ✅ **PRECISE**  
**推荐:** 可以安全wiring

**关键原则 (CRITICAL):**
```
Runtime B: TOOL_EXECUTED = TRUE
Runtime B: CHECKPOINT_CONFLICT = TRUE

Both records must be preserved.
Do NOT model conflict as undoing execution history.
```

---

### B10. COMPLETED

| 维度 | 值 |
|------|------|
| **语义事实** | ❓ **语义模糊 — 需要明确定义** |
| **候选边界** | A. 模型返回最终答案<br/>B. CHECK B delete成功<br/>C. ChatMemory最终assistant持久化<br/>D. AgentResult返回 |

**语义分析:**

**Option A: Model returned final answer**
- ❌ 过早 — CHECK B可能失败

**Option B: CHECK B delete committed** ✅ **推荐（Checkpoint authority）**
- ✅ "进程不再可恢复 = 完成"
- Checkpoint = recovery authority
- Checkpoint deleted = no longer resumable = completed

**Option C: ChatMemory final assistant persisted**
- ⚠️ 也重要 — 但ChatMemory是conversation authority
- 如果checkpoint已删除但ChatMemory写入失败，谁是权威？

**Option D: AgentResult returned**
- ❌ 太晚 — 只是API层面

**推荐定义:**

```
COMPLETED = "Process reached terminal state and checkpoint deleted (no longer resumable)"
```

**精确提交点:** CHECK B deleteIfVersion()返回true

| 维度 | 值（基于Option B） |
|------|------|
| **语义事实** | 进程完成，checkpoint已删除，不再可恢复 |
| **精确提交点** | CHECK B deleteIfVersion()成功 |
| **相对checkpoint操作** | IMMEDIATELY AFTER CHECK B delete |
| **相对工具副作用** | AFTER — 所有工具已执行 |
| **相对ChatMemory写入** | ⚠️ **BEFORE** — 存在crash window |
| **CHECK B失败后仍TRUE?** | N/A — CHECK B必须成功 |
| **审计关键?** | HIGH — 完成审计 |
| **恢复关键?** | YES — 标记不再可恢复 |
| **Ledger append失败应阻止执行?** | ⚠️ Debatable — checkpoint已删除，无法撤销 |
| **最小payload** | `{"checkpointVersion": N, "finalContent": "...", "totalEvidences": M}` |

**语义评估:** ✅ **可以冻结为此定义**

**关键crash window (CANNOT SOLVE IN M6-T1):**
```
CHECK B deleteIfVersion() succeeds
ledger.append(COMPLETED) ← may fail
chatMemory.add(finalAssistant) ← may fail
return AgentResult
```

**可能状态:**
1. ✅ All succeed → consistent
2. ❌ Checkpoint deleted, COMPLETED recorded, ChatMemory failed → conversation incomplete
3. ❌ Checkpoint deleted, COMPLETED append failed → audit incomplete
4. ❌ Checkpoint deleted, both ledger and ChatMemory failed → worst case

**推荐策略:**
- COMPLETED append失败不应阻止返回AgentResult（checkpoint已删除，不可恢复）
- 记录append失败到logs
- 未来outbox pattern或shared transaction改进一致性

### B11. FAILED

| 维度 | 值 |
|------|------|
| **语义事实** | ❓ **语义模糊 — 需要明确定义** |
| **当前M5路径** | 未明确实现（大多数失败抛异常而非记录FAILED event） |

**语义分析:**

FAILED可能表示:
- Terminal non-retryable execution failure
- 与COMPLETED对称的失败终止
- Checkpoint应该删除？还是保留用于诊断？

**当前M5行为:**
- ResumePreparationException → 抛出异常，checkpoint保留
- CheckpointTransitionConflictException → 抛出异常，checkpoint可能被winner删除
- 工具执行失败 → 通常不是terminal，可能re-suspend

**推荐定义:**

```
FAILED = "Process reached terminal failure state, checkpoint deleted (no longer retryable)"
```

**但需要区分:**
- Retryable failure (checkpoint保留)
- Terminal failure (checkpoint删除)

| 维度 | 值（provisional） |
|------|------|
| **语义事实** | 进程终止性失败，不再可重试 |
| **精确提交点** | TBD — M5未明确实现 |
| **相对checkpoint操作** | TBD — 应该DELETE? |
| **相对工具副作用** | 可能AFTER |
| **相对ChatMemory写入** | TBD |
| **CHECK B失败后仍TRUE?** | TBD |
| **审计关键?** | HIGH |
| **恢复关键?** | YES |
| **Ledger append失败应阻止执行?** | NO |
| **最小payload** | `{"failureType": "...", "errorMessage": "...", "checkpointVersion": N}` |

**语义评估:** ❌ **TOO AMBIGUOUS TO WIRE IN M6-T2**

**推荐:** 
1. **暂不wiring FAILED** — 语义不清晰
2. **M5当前依赖异常传播** — 保持此行为
3. **未来M6+定义failure classification** — 再引入FAILED event

## D. 写入顺序矩阵

### D1. 初始执行 → 首次暂停

**写入顺序:**

```
1. UserMessage → ChatMemory (by MessageChatMemoryAdvisor before execute)
2. 模型调用 → AssistantMessage(toolCalls) generated
3. AssistantMessage → ChatMemory (by MessageChatMemoryAdvisor after model)
4. Governance decision: REQUIRE_APPROVAL
5. [Event: APPROVAL_REQUIRED]  ← 候选append点
6. SuspensionCheckpoint.create() ← DURABLE COMMIT
7. [Event: SUSPENDED]  ← 候选append点
8. return AgentResult(process)
```

**推荐append顺序:**
```
5. ledger.append(APPROVAL_REQUIRED, v=null, payload)  ← 在checkpoint前
7. ledger.append(SUSPENDED, v=1, payload)  ← 在checkpoint create后
```

**crash windows:**
- Checkpoint create成功，SUSPENDED append失败 → checkpoint可恢复，但无审计记录

---

### D2. 批准恢复 → 完成

**写入顺序:**

```
1. resumeProcess(APPROVED) called
2. [Event: APPROVAL_GRANTED]  ← 候选append点（CHECK A前或后?）
3. Checkpoint.load() — CHECK A
4. RuntimeBinding.resolve()
5. [Event: RESUMED]  ← 候选append点（CHECK A后）
6. ProtocolReconstructor.executeApprovedBatch()
   6a. ToolCallback.execute() → 副作用发生
   6b. Evidence收集
   6c. [Event: TOOL_EXECUTED]  ← 候选append点（每个工具执行后）
   6d. ToolResponseMessage生成
7. 模型continuation调用
8. 模型返回最终答案
9. CHECK B deleteIfVersion() ← DURABLE COMMIT
10. [Event: COMPLETED]  ← 候选append点（CHECK B后）
11. ChatMemory.add(finalAssistant)
12. return AgentResult
```

**推荐append顺序:**
```
2. ledger.append(APPROVAL_GRANTED, v=N, payload)  ← CHECK A之前（决策独立）
5. ledger.append(RESUMED, v=N, payload)  ← CHECK A通过后
6c. for each tool: ledger.append(TOOL_EXECUTED, v=N, payload)  ← 工具返回后立即
10. ledger.append(COMPLETED, v=N, payload)  ← CHECK B delete后
```

**crash windows:**
- APPROVAL_GRANTED append失败 → 工具可能执行但无批准审计（⚠️ 合规风险）
- TOOL_EXECUTED append失败 → 副作用发生但无审计（⚠️ 不可阻止）
- CHECK B成功，COMPLETED append失败 → checkpoint已删除，审计不完整
- CHECK B成功，COMPLETED记录，ChatMemory失败 → conversation不完整

---

### D3. 批准恢复 → 重新暂停

**写入顺序:**

```
1-6c. 同上（工具执行，TOOL_EXECUTED记录）
7. 模型返回新AssistantMessage(toolCalls)
8. Governance decision: REQUIRE_APPROVAL
9. [Event: APPROVAL_REQUIRED]  ← 候选append点
10. SuspensionCheckpoint v→v+1
11. CHECK B replaceIfVersion() ← DURABLE COMMIT
12. [Event: SUSPENDED]  ← 候选append点（新version）
13. return AgentResult(process)
```

**推荐append顺序:**
```
9. ledger.append(APPROVAL_REQUIRED, v=N, payload)  ← CHECK B前
12. ledger.append(SUSPENDED, v=N+1, payload)  ← CHECK B replace后
```

**crash windows:**
- CHECK B replace成功，SUSPENDED(v+1) append失败 → 新checkpoint可恢复，但无审计

---

### D4. CHECK B冲突

**Runtime B写入顺序（loser）:**

```
1-6c. 工具执行，TOOL_EXECUTED append成功
7-8. 模型调用
9. CHECK B deleteIfVersion() → FALSE ❌
10. [Event: CHECKPOINT_CONFLICT]  ← 候选append点
11. throw CheckpointTransitionConflictException
```

**推荐append顺序:**
```
6c. ledger.append(TOOL_EXECUTED, v=N, payload)  ← 已成功
10. ledger.append(CHECKPOINT_CONFLICT, v=N, payload)  ← CHECK B失败后
```

**关键原则:**
- TOOL_EXECUTED已记录，必须保留
- CHECKPOINT_CONFLICT追加，不删除TOOL_EXECUTED
- 两者共存表示"执行了但未赢得checkpoint转换"

## E. Ledger失败策略

### E1. 失败分类

| Event | Append失败可以阻止执行? | 理由 |
|-------|----------------------|------|
| PROCESS_STARTED | ❌ NO | 进程创建不依赖ledger |
| APPROVAL_REQUIRED | ❌ NO | Governance决策已发生，应该suspend |
| APPROVAL_GRANTED | ⚠️ **DEPENDS ON COMPLIANCE** | 如果合规要求必须审计批准，可能需要阻止 |
| APPROVAL_REJECTED | ⚠️ DEPENDS ON COMPLIANCE | 同上 |
| SUSPENDED | ❌ NO | Checkpoint已创建（可恢复），append失败不影响恢复 |
| RESUMED | ❌ NO | 已经在恢复中，阻止无意义 |
| TOOL_EXECUTED | ❌ **CANNOT BLOCK** | 副作用已发生，抛异常不撤销 |
| TOOL_FAILED | ❌ NO | 失败已发生 |
| CHECKPOINT_CONFLICT | ❌ NO | CHECK B已失败，进程终止 |
| COMPLETED | ❌ NO | Checkpoint已删除，无法撤销 |
| FAILED | ❌ NO | 终止已发生 |

### E2. 推荐策略分级

**Audit-Critical Events (高风险，可能需要阻止):**
- APPROVAL_GRANTED
- APPROVAL_REJECTED

**推荐:** 提供配置选项
```java
@ConfigurationProperties("arctra.ledger")
public class LedgerPolicy {
  boolean strictApprovalAudit = false;  // 默认relaxed
  
  // if true: APPROVAL_GRANTED/REJECTED append失败 → throw exception
  // if false: 记录到logs + 告警，允许继续
}
```

**Cannot-Block Events (副作用已发生):**
- TOOL_EXECUTED
- TOOL_FAILED
- COMPLETED

**策略:** 永远不能阻止执行，只能:
1. 记录append失败到logs (ERROR level)
2. 发送告警（审计不完整）
3. 允许后续reconciliation scanner补录

**Best-Effort Events (审计重要但不阻止):**
- PROCESS_STARTED
- APPROVAL_REQUIRED
- SUSPENDED
- RESUMED
- CHECKPOINT_CONFLICT

**策略:** 记录失败到logs，继续执行

|------|------|------|

### F2. 关系模型（未来EvidenceStore后）

```
ExecutionRecord #17:

  eventType = TOOL_EXECUTED

    "toolCallId": "TC88",
    "toolName": "restartServer",
```

## H. Durable Plane vs Observability Plane

### H1. 两个平面定义（冻结）

**Durable Plane（正确性/恢复/审计）:**
- Checkpoint → 当前恢复状态
- ExecutionLedger → 历史执行事实
- Evidence → 执行证明内容
- ChatMemory → 对话历史

**特征:**
- 必须持久化
- 正确性关键
- 恢复依赖
- append失败可能影响执行正确性（取决于event）

---

**Observability Plane（调试/性能/运维）:**
- Logs → 诊断消息
- Metrics → 聚合计数/时延
- Traces/Spans → 分布式追踪

**特征:**
- Best-effort delivery
- 非正确性关键
- 恢复不依赖
- append失败不影响执行正确性

---

### H2. 关键规则（冻结）

**规则1:** Logs/traces永远不能成为恢复正确性的唯一依赖

**规则2:** 删除日志不影响恢复

**规则3:** Trace backend不可用不阻止checkpoint correctness

**规则4:** ExecutionLedger append失败的语义与log append失败完全不同

## J. 关联ID模型（冻结）

### J1. Domain IDs (Arctra语义定义)

| ID | 作用域 | 所有者 | 稳定性 |
|----|-------|--------|--------|

| **checkpointVersion** | 暂停episode | CheckpointStore | 递增 (1→2→3) |
| **recordId** | ExecutionRecord | ExecutionLedger | 唯一 (processId:sequence) |

| **evidenceId** | Evidence | EvidenceStore (future) | 唯一 |
| **runtimeId** | Runtime instance | Application (future) | Per-instance |
| **sessionId** | Conversation | Application | 跨turns稳定 |
| **turnId** | Conversation turn | Future | Turn lifetime |
| **stepId** | Execution step | Future | Step lifetime |
| **operationId** | External operation | Future | 幂等性key |

| **spanId** | Operation | OpenTelemetry/APM | Span lifetime |

#### TOOL_EXECUTED语义明确化

**当前M6-T1 Javadoc:**
> "Framework-observed tool callback execution returned successfully."
> 
> "Provisional semantics: Tool callback returned successfully. Does not yet distinguish dispatch/acknowledgement/external-receipt."

**M6-T1.5增强Javadoc:**

```java
/**
 * Framework-observed tool callback execution returned successfully.
 *
 * <p><strong>Provisional semantics:</strong> The tool callback invoked by the framework returned
 * without throwing an exception. This does NOT guarantee:
 *
 * <ul>
 *   <li>External side effect is transactionally committed
 *   <li>External system executed exactly once
 *   <li>Operation receipt has been verified
 *   <li>Callback return value represents confirmed success (vs uncertain outcome)
 * </ul>
 *
 * <p><strong>Examples of uncertain outcomes currently classified as TOOL_EXECUTED:</strong>
 * <ul>
 *   <li>Tool sends async request, returns immediately with "queued" status
 *   <li>Tool returns before remote operation completes
 *   <li>Tool timeout but remote operation may have succeeded
 * </ul>
 *
 * <p>Semantics will be refined with:
 * <ul>
 *   <li>operationId — Idempotency keys for external operations
 *   <li>External receipts — Confirmed operation completion from external system
 *   <li>UNCERTAIN_OUTCOME event type — Distinguish known success from uncertain
 * </ul>
 *
 * <p><strong>Critical for at-least-once semantics:</strong> If a tool executed but CHECK B later
 * loses, TOOL_EXECUTED record remains TRUE. Do not assume CHECK B failure means tool did not
 * execute — external side effects are not transactional with checkpoint.
 */
TOOL_EXECUTED
```

---

#### TOOL_FAILED语义明确化

**增强Javadoc:**

```java
/**
 * Framework-observed tool callback execution failed.
 *
 * <p><strong>Provisional semantics:</strong> The tool callback threw an exception or returned
 * an error status. This does NOT guarantee:
 *
 * <ul>
 *   <li>External side effect did not occur
 *   <li>Operation definitely failed on external system
 *   <li>Operation is safe to retry without idempotency
 * </ul>
 *
 * <p><strong>Examples of uncertain failures:</strong>
 * <ul>
 *   <li>Network timeout — remote operation may have succeeded
 *   <li>Callback throws after sending request but before receiving response

```

| Crash Window | Checkpoint状态 | Ledger状态 | ChatMemory状态 | 可容忍? | 未来改进方案 |
|-------------|--------------|-----------|---------------|--------|------------|

## 附录: 关键原则速查表

### 提交边界原则

1. **Event = 已成为true的事实** （不是intention或speculation）
2. **Checkpoint权威 ≠ Ledger权威** （recovery vs history）
3. **CHECK B loser的历史必须保留** （不能假装没执行）
4. **副作用发生后不能通过ledger append失败撤销**
5. **Audit-critical events需要配置策略**

### 投影原则

1. **一个事实,多个投影** （不是重复）
2. **Durable plane ≠ Observability plane** （correctness vs debugging）
3. **Recovery永远不依赖logs/traces**
4. **Domain IDs ≠ Observability IDs** （processId ≠ traceId）
5. **删除日志不影响恢复**

### Wiring原则

1. **语义unclear的event暂不wiring**
2. **Cannot-block events永远不能因append失败阻止**
3. **Audit-critical events提供strict/relaxed模式**
4. **Crash windows记录但不强求解决**
5. **渐进式wiring，从清晰语义开始**
