## A. 发现的不一致性

### A1. APPROVAL_GRANTED边界冲突

**冲突1 — 时序矛盾:**

M6-T1.5报告Section D2推荐:
```
2. ledger.append(APPROVAL_GRANTED, v=N, payload)  ← CHECK A之前（决策独立）
5. ledger.append(RESUMED, v=N, payload)  ← CHECK A通过后
```

**冲突2 — 语义矛盾:**

M6-T1.5报告Section B4正确识别:
> "CHECK B失败后仍TRUE? YES — 批准决策确实发生，即使后续CHECK B失败"

但如果APPROVAL_GRANTED在CHECK A之前记录，会产生:
```
resumeProcess(processId=P100, checkpointVersion=3, APPROVED)
→ ledger.append(APPROVAL_GRANTED, v=3)  ← 记录成功
→ CHECK A
→ actual checkpoint version = 4  ← version mismatch!
→ throw StaleCheckpointException
```

**结果:** Ledger包含`APPROVAL_GRANTED(v=3)`，但v3已经stale，批准从未对有效checkpoint生效。

**根本问题:** APPROVAL_GRANTED语义应该是"批准决策应用于**当前有效**checkpoint"，不是"收到批准信号"。

---

### A2. RESUMED边界冲突

**冲突1 — 定义矛盾:**

M6-T1.5报告Section B6冻结:
> "精确提交点: CHECK A通过后"

**冲突2 — 场景矛盾:**

M6-T1.5报告Section A6正确分析:
```
CHECK A通过
binding = bindingResolver.resolve(...)
→ throw exception (resolver失败)
  ↓
catch ResumePreparationException
→ 包装并抛出到caller
```

然后正确结论:
> "RESUMED不成立 — 绑定解析失败"

**问题:** 如果"RESUMED = CHECK A通过后"，那么在ResumePreparationException场景中，CHECK A已通过，但RESUMED不应成立。矛盾。

**根本问题:** CHECK A只验证checkpoint版本有效性，不足以表示"成功准备好恢复执行"。

## B. 修正后的APPROVAL_GRANTED边界

### B1. 语义冻结

```
APPROVAL_GRANTED =
"An APPROVED continuation signal has been validated against 
the CURRENT checkpoint episode, and execution will proceed 
with approved tool batch."
```

**关键要求:**
1. Checkpoint version已验证当前（CHECK A通过）
2. RuntimeBinding已解析（恢复能力已确认）
3. APPROVED signal已接受

**不是:**
- ❌ "收到批准信号" — 那是未来的APPROVAL_SIGNAL_RECEIVED
- ❌ "批准决策独立于checkpoint" — 批准必须对应有效checkpoint

---

### B2. 精确提交边界

**修正后时间线:**

```
1. resumeProcess(processId, checkpointVersion, APPROVED)
   ↓
2. CHECK A:
   checkpoint = checkpointStore.load(processId)
   if (checkpoint.checkpointVersion != expectedVersion)
     → throw StaleCheckpointException  ← 无APPROVAL_GRANTED记录
   ✅ CHECK A通过
   ↓
3. RuntimeBinding resolution:
   binding = bindingResolver.resolve(processId, runtimeBindingKey, sessionId)
   if (fails)
     → throw ResumePreparationException  ← 无APPROVAL_GRANTED记录
   ✅ Binding resolved
   ↓
4. Validate/accept APPROVED signal
   (signal已知与current checkpoint关联)
   ✅ Signal validated
   ↓
5. ✅ APPROVAL_GRANTED becomes TRUE
   ledger.append(APPROVAL_GRANTED, checkpointVersion, payload)
   ↓
6. RESUMED preparation (见Section D)
```

**精确提交点:** CHECK A通过 **AND** RuntimeBinding resolved **AND** signal validated

---

### B3. 失败场景保证

**Scenario A — CHECK A失败:**
```
resumeProcess(v=3, APPROVED)
CHECK A → current version = 4
throw StaleCheckpointException

Records: 无APPROVAL_GRANTED
```

**Scenario B — RuntimeBinding失败:**
```
resumeProcess(v=3, APPROVED)
CHECK A passes (v=3 current)
RuntimeBindingResolver fails
throw ResumePreparationException

Records: 无APPROVAL_GRANTED
```

**Scenario C — 正常通过:**
```
resumeProcess(v=3, APPROVED)
CHECK A passes
RuntimeBinding resolves
Signal validated
→ APPROVAL_GRANTED(v=3)
→ 继续执行
```

### B4. Javadoc修正

```java
/**
 * Human granted approval for pending tool execution.
 *
 * <p><strong>Precise semantics:</strong> An APPROVED continuation signal has been validated
 * against the current checkpoint episode (CHECK A passed), runtime binding successfully
 * resolved, and execution will proceed with the approved tool batch.
 *
 * <p><strong>Commit boundary:</strong> This event becomes true AFTER:
 * <ol>
 *   <li>CHECK A validates checkpoint version is current
 *   <li>RuntimeBindingResolver successfully reconstructs execution binding
 *   <li>APPROVED signal is validated/accepted for current checkpoint
 * </ol>
 *
 * <p>If CHECK A fails (StaleCheckpointException) or RuntimeBindingResolver fails
 * (ResumePreparationException), NO APPROVAL_GRANTED record is created.
 *
 * <p><strong>Audit-critical:</strong> This event represents a confirmed governance decision
 * applied to a valid checkpoint. If ledger append fails after the decision is validated,
 * execution MAY proceed (depending on compliance requirements), but audit trail is incomplete.
 *
 * <p><strong>Future distinction:</strong> This event represents validated approval for current
 * checkpoint. If future requirements need to record raw approval signal submissions (including
 * stale/invalid), introduce a separate event type like APPROVAL_SIGNAL_RECEIVED.
 */
APPROVAL_GRANTED,
```

## D. 修正后的RESUMED边界

### D1. 语义冻结

```
RESUMED =
"The durable continuation environment has been successfully 
prepared from the current checkpoint, and control is entering 
resumed execution path (approved or rejected)."
```

**关键要素:**
1. Checkpoint version已验证当前（CHECK A）
2. RuntimeBinding已成功解析（定义+上下文可用）
3. ContinuationSignal已验证/接受
4. 准备进入恢复执行路径（工具执行或拒绝响应）

---

### D2. 精确提交边界

**修正后时间线:**

```
1. resumeProcess(signal)
   ↓
2. CHECK A passes
   ↓
3. RuntimeBinding resolves
   ↓
4. Signal validated → APPROVAL_GRANTED or APPROVAL_REJECTED
   ↓
5. ✅ RESUMED becomes TRUE
   ledger.append(RESUMED, checkpointVersion, payload)
   ↓
6. Enter resumed execution path:
   - If APPROVED: reconstructAndExecuteApproved()
   - If REJECTED: reconstructDenialResponses()
```

**精确提交点:** CHECK A通过 **AND** RuntimeBinding resolved **AND** APPROVAL_GRANTED/REJECTED recorded

---

### D3. 与APPROVAL_*的关系

**时序:**
```
APPROVAL_GRANTED/REJECTED  ← 先记录（治理决策）
RESUMED                    ← 后记录（恢复准备完成）
```

**语义区分:**

| Event | 语义 |
|-------|------|
| APPROVAL_GRANTED | 批准决策已验证并应用于当前checkpoint |
| RESUMED | 恢复执行环境已成功准备，即将进入continuation |

**为什么需要两个事件?**

1. **治理审计 vs 技术恢复** — 批准决策是governance concern，恢复是runtime concern
2. **失败点不同** — APPROVAL_GRANTED成功不保证RESUMED成功（虽然当前M5很少失败）
3. **未来扩展** — 可能有RESUMED但无APPROVAL_*（其他类型的resume，如manual retry）

---

### D4. 失败场景保证

**Scenario A — CHECK A失败:**
```
resumeProcess(v=3, APPROVED)
CHECK A fails

Records: 
- 无APPROVAL_GRANTED
- 无RESUMED
```

**Scenario B — RuntimeBinding失败:**
```
resumeProcess(v=3, APPROVED)
CHECK A passes
RuntimeBindingResolver fails

Records:
- 无APPROVAL_GRANTED
- 无RESUMED
```

**Scenario C — 正常通过:**
```

CHECK A passes
RuntimeBinding resolves
→ APPROVAL_GRANTED(v=3)
→ RESUMED(v=3)

```

### D5. Javadoc修正

```java
/**
 * Process resumed from checkpoint.
 *
 * <p><strong>Precise semantics:</strong> The durable continuation environment has been
 * successfully prepared from the current checkpoint (CHECK A passed, RuntimeBinding resolved),
 * continuation signal validated (APPROVAL_GRANTED or APPROVAL_REJECTED), and control is
 * entering resumed execution path.
 *
 * <p><strong>Commit boundary:</strong> This event becomes true AFTER:
 * <ol>
 *   <li>CHECK A validates checkpoint version is current
 *   <li>RuntimeBindingResolver successfully reconstructs execution binding
 *   <li>ContinuationSignal validated (APPROVAL_GRANTED or APPROVAL_REJECTED recorded)
 *   <li>Ready to enter resumed execution (tool execution or rejection responses)
 * </ol>
 *
 * <p><strong>Failure scenarios:</strong>
 * <ul>
 *   <li>CHECK A fails (StaleCheckpointException) → NO RESUMED

 * </ul>
 *
 * <p><strong>Distinction from APPROVAL_GRANTED/REJECTED:</strong> Approval events represent
 * governance decisions validated for the checkpoint. RESUMED represents successful preparation
 * of the runtime continuation environment. Both must succeed for execution to proceed.
 *
 * <p>If ledger append fails, resume execution MAY proceed (runtime already prepared), but
 * audit trail is incomplete.
 */
RESUMED,
```

## E. ResumePreparationException时间线

### E1. 完整时间线

```
1. resumeProcess(processId, checkpointVersion, signal)
   ↓
2. CHECK A:
   checkpoint = checkpointStore.load(processId)
   if (checkpoint.checkpointVersion != expectedVersion)
     → throw StaleCheckpointException
   ✅ CHECK A passes
   ↓
3. RuntimeBinding resolution:
   try {
     binding = bindingResolver.resolve(processId, runtimeBindingKey, sessionId)
   } catch (Exception e) {
     throw new ResumePreparationException(
       "RuntimeBinding resolution failed for processId " + processId,
       e
     )
   }
   ❌ Binding resolution fails
   ↓
4. throw ResumePreparationException → propagates to caller
```

**创建的ExecutionRecord:**
- ❌ 无APPROVAL_GRANTED
- ❌ 无APPROVAL_REJECTED  
- ❌ 无RESUMED
- ❌ 无TOOL_EXECUTED
- ❌ 无COMPLETED/SUSPENDED/CHECKPOINT_CONFLICT

**Checkpoint状态:**
- ✅ 仍然存在，version未变
- ✅ 可以重试resume（如果binding问题解决）

---

### E2. 不变式

```
ResumePreparationException thrown
⇒ NO APPROVAL_GRANTED/REJECTED record
⇒ NO RESUMED record
⇒ Checkpoint remains current and retryable
```

---

### E3. 未来扩展（不在M6-T2实现）

**如果需要审计失败的resume尝试:**

引入新事件:
```java
/**
 * Resume attempt failed during preparation phase.
 *
 * <p>CHECK A passed (checkpoint is current), but RuntimeBindingResolver failed.
 * No execution occurred. Checkpoint remains current and retryable.
 */
RESUME_PREPARATION_FAILED,
```

**但M6-T2不添加此事件** — 当前依赖异常传播即可。

## F. 修正后的批准/拒绝恢复时间线

### F1. 批准恢复完整时间线

```
1. resumeProcess(processId, checkpointVersion=N, APPROVED)
   ↓
2. CHECK A passes (checkpoint vN is current)
   ↓
3. RuntimeBinding resolves (definition + context)
   ↓
4. Validate/accept APPROVED signal
   ↓
5. ledger.append(APPROVAL_GRANTED, v=N, payload)
   ↓
6. ledger.append(RESUMED, v=N, payload)
   ↓
7. reconstructAndExecuteApproved():
   a. Load conversationHistory from ChatMemory
   b. ProtocolReconstructor.executeApprovedBatch(pendingBatch)
      i. Rebuild AssistantMessage(toolCalls)
      ii. toolCallingManager.executeToolCalls()
          → ToolCallback.execute() for each tool
          → ❗ SIDE EFFECTS OCCUR
          → Evidence collected
          → ledger.append(TOOL_EXECUTED, v=N, payload)  ← 每个成功工具
          OR
          → ledger.append(TOOL_FAILED, v=N, payload)   ← 每个失败工具
      iii. Build ToolResponseMessage(results)
      iv. Return continuationMessages
   ↓
8. Merge evidences (historical + new)
   ↓
9. Model continuation:
   content = promptSpec.call().content()
   → 可能返回最终答案
   OR
   → 抛出ToolApprovalRequiredSignal (re-suspension)
   ↓
10. 假设完成路径:
    CHECK B DELETE:
    deleted = checkpointStore.deleteIfVersion(processId, vN)
    if (!deleted)
      → ledger.append(CHECKPOINT_CONFLICT, v=N, payload)
      → throw CheckpointTransitionConflictException
    ✅ CHECK B succeeds
    ↓
11. ledger.append(COMPLETED, v=N, payload)
    ↓
12. persistCompletedAssistant(context, content)
    → chatMemory.add(sessionId, AssistantMessage(content))
    ↓
13. return new AgentResult(content, mergedEvidences)
```

---

### F2. 拒绝恢复完整时间线

```
1. resumeProcess(processId, checkpointVersion=N, REJECTED)
   ↓
2. CHECK A passes
   ↓
3. RuntimeBinding resolves
   ↓
4. Validate/accept REJECTED signal
   ↓
5. ledger.append(APPROVAL_REJECTED, v=N, payload)
   ↓
6. ledger.append(RESUMED, v=N, payload)
   ↓
7. reconstructDenialResponses():
   a. Rebuild AssistantMessage(toolCalls) from pendingBatch
   b. Build denial ToolResponseMessage(每个tool返回"rejected")
   c. Return continuationMessages = [history + AssistantMessage + denial]
   ❗ 无真实工具执行，无TOOL_EXECUTED
   ↓
8. Model continuation:
   content = promptSpec.call().content()
   → 模型观察rejection并生成最终答案
   ↓
9. CHECK B DELETE:
   deleted = checkpointStore.deleteIfVersion(processId, vN)
   if (!deleted)
     → ledger.append(CHECKPOINT_CONFLICT, v=N, payload)
     → throw CheckpointTransitionConflictException
   ✅ CHECK B succeeds
   ↓
10. ledger.append(COMPLETED, v=N, payload)
    ↓
11. persistCompletedAssistant(context, content)
    ↓
12. return new AgentResult(content, evidences)
```

---

### F3. 重新暂停时间线

```
1-7b. 同批准恢复（工具执行完成）
   ↓
8. Merge evidences
   ↓
9. Model continuation:
   content = promptSpec.call().content()
   → 模型返回新的AssistantMessage(toolCalls=[...])
   → GovernanceToolCallingAdvisor拦截
   → GovernanceDecision = REQUIRE_APPROVAL
   → 抛出ToolApprovalRequiredSignal
   ↓
catch ToolApprovalRequiredSignal:
   ↓
10. ledger.append(APPROVAL_REQUIRED, v=N, payload)
    ↓
11. Build newCheckpoint(
      processId (same)
      checkpointVersion = N+1
      pendingBatch = new toolCalls
      accumulatedEvidences = mergedEvidences
    )
    ↓
12. CHECK B REPLACE:
    replaced = checkpointStore.replaceIfVersion(processId, vN, newCheckpoint)
    if (!replaced)
      → ledger.append(CHECKPOINT_CONFLICT, v=N, payload)
      → throw CheckpointTransitionConflictException
    ✅ CHECK B succeeds
    ↓
13. ledger.append(SUSPENDED, v=N+1, payload)
    ↓
14. ProcessFactory.createDurableSuspended(processId, N+1, this)
    ↓
15. return new AgentResult(partialContent, mergedEvidences, process)
```

## G. 确认COMPLETED边界

### G1. 语义确认（无变更）

```
COMPLETED =
"Process reached terminal state and checkpoint deleted 
(no longer resumable)."
```

**权威依据:** Checkpoint是recovery authority

**逻辑:**
```
Checkpoint deleted
⇒ Process no longer resumable
⇒ COMPLETED (from recovery perspective)
```

---

### G2. 精确提交边界确认

**时间线:**
```
Model returns final answer
↓
CHECK B DELETE:
deleted = checkpointStore.deleteIfVersion(processId, checkpointVersion)
if (!deleted)
  → CHECKPOINT_CONFLICT
  → throw exception
✅ Checkpoint deleted
↓
✅ COMPLETED becomes TRUE
ledger.append(COMPLETED, checkpointVersion, payload)
↓
persistCompletedAssistant(context, content)
→ chatMemory.add(...)
→ ⚠️ may fail (crash window)
↓
return AgentResult
```

**精确提交点:** CHECK B deleteIfVersion()返回true

---

### G3. Crash Window承认

**场景:**
```
CHECK B deleteIfVersion() succeeds
ledger.append(COMPLETED) may fail
chatMemory.add(finalAssistant) may fail
```

**可能结果:**

| Checkpoint | Ledger | ChatMemory | 状态 |
|-----------|--------|-----------|------|
| ✅ Deleted | ✅ COMPLETED | ✅ Final assistant | 一致 |
| ✅ Deleted | ❌ 无COMPLETED | ✅ Final assistant | 审计不完整 |
| ✅ Deleted | ✅ COMPLETED | ❌ 无final assistant | 对话不完整 |
| ✅ Deleted | ❌ 无COMPLETED | ❌ 无final assistant | 最坏情况 |

**M6-T1.5.1立场:** ✅ **承认crash window，不在M6-T2解决**

**理由:**
1. Checkpoint已删除，不可撤销
2. ledger append失败不能阻止返回AgentResult（checkpoint已gone）
3. ChatMemory失败不能阻止返回（内容已生成）
4. 这是跨权威一致性问题，需要M7+ outbox/shared-transaction解决

---

### G4. 不改变COMPLETED定义

**不采纳的备选定义:**

❌ **"ChatMemory最终assistant持久化成功"**
- 理由：ChatMemory是conversation authority，不是recovery authority
- 如果checkpoint已删除但ChatMemory失败，进程仍然是"completed"从recovery视角

❌ **"模型返回最终答案"**
- 理由：过早，CHECK B可能失败

❌ **"AgentResult返回"**
- 理由：太晚，只是API层面

**保持:** ✅ **Checkpoint deleted = COMPLETED**

---

### G5. Javadoc确认（可选增强）

当前M6-T1 Javadoc已基本正确，可选增强:

```java
/**
 * Process completed (terminal state).
 *
 * <p><strong>Precise semantics:</strong> Process reached terminal state and checkpoint
 * deleted (no longer resumable). Checkpoint is recovery authority; checkpoint deletion
 * marks completion from recovery perspective.
 *
 * <p><strong>Commit boundary:</strong> CHECK B deleteIfVersion() succeeds.
 *
 * <p><strong>Cross-authority consistency:</strong> COMPLETED is recorded AFTER checkpoint
 * deletion but BEFORE final ChatMemory assistant persistence. If ChatMemory write fails,
 * conversation may be incomplete while process is marked completed. This is an acknowledged
 * cross-authority consistency debt, not a reason to redefine COMPLETED.
 *
 * <p>If ledger append fails, process is still completed (checkpoint gone), but audit trail
 * is incomplete. Append failure cannot block return or undo checkpoint deletion.
 */
COMPLETED
```

## H. TOOL_EXECUTED + CHECKPOINT_CONFLICT不变式

### H1. 不变式确认（无变更）

```
Runtime B executes tools
→ TOOL_EXECUTED records created
→ CHECK B fails (concurrent modification)
→ CHECKPOINT_CONFLICT recorded

Both records MUST remain in ledger.
```

**关键原则（冻结）:**

**永远不要将CHECKPOINT_CONFLICT视为撤销工具执行历史。**

---

### H2. 场景示例

**Runtime A和B都通过CHECK A (v3):**

```
Runtime A:
  CHECK A pass (v3)
  RuntimeBinding resolve
  APPROVAL_GRANTED(v3)
  RESUMED(v3)
  Tool "restartServer" executes → 副作用发生
  TOOL_EXECUTED(v3, toolName="restartServer")
  Model continuation
  CHECK B deleteIfVersion(v3) → TRUE ✅
  COMPLETED(v3)
  return SUCCESS

Runtime B (并发):
  CHECK A pass (v3) ✅ 同样通过
  RuntimeBinding resolve
  APPROVAL_GRANTED(v3)
  RESUMED(v3)
  Tool "restartServer" executes → ❗副作用再次发生 (duplicate execution)
  TOOL_EXECUTED(v3, toolName="restartServer")  ← 必须记录!
  Model continuation
  CHECK B deleteIfVersion(v3) → FALSE ❌ (A已经删除)
  CHECKPOINT_CONFLICT(v=3, operation="DELETE")  ← 追加记录
  throw CheckpointTransitionConflictException
```

---

### H3. Ledger最终状态（Runtime B视角）

