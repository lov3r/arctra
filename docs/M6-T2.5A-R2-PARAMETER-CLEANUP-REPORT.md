## B. ToolObservationContext

### Final Type

```java
record ToolObservationContext(
    String processId,
    long checkpointVersion,
    ExecutionEventListener eventListener) {

  ToolObservationContext {
    Objects.requireNonNull(processId, "processId cannot be null");
    Objects.requireNonNull(eventListener, "eventListener cannot be null");

    if (processId.isBlank()) {
      throw new IllegalArgumentException("processId cannot be blank");
    }

    if (checkpointVersion <= 0) {
      throw new IllegalArgumentException(
          "checkpointVersion must be positive, was: " + checkpointVersion);
    }
  }
}
```

**Fields**:
- `String processId` - stable process identifier from checkpoint (required, non-blank)
- `long checkpointVersion` - current checkpoint version (required, positive)
- `ExecutionEventListener eventListener` - event sink for tool observation (required, non-null)

**Visibility**: `package-private` (not part of public API)

**Validation**:
- Compact constructor validates all fields at construction
- Null or invalid values rejected immediately
- Clear error messages for violations

**Exact Responsibility**:
> Correlation context for tool execution observation during checkpoint-backed durable resumed execution.

**Does NOT own**:
- ❌ toolCallId (deferred - not yet part of correlation)
- ❌ operationId / attemptId (not yet implemented)
- ❌ retry metadata (not yet implemented)
- ❌ Evidence instances (separate authority)
- ❌ Spring AI Message types (protocol layer concern)
- ❌ Checkpoint reference (authority boundary separation)

public String call(String functionArguments) {

## L. R3 Readiness

### 1. Is tool observation plumbing now contained?

**Answer: YES ✅**

**Evidence**:
- 3 event context parameters → 1 cohesive ToolObservationContext
- No null-heavy positional plumbing
- Clear semantic boundary (observationContext == null means no events)
- Tests use explicit no-observation overload

### 2. Does ProtocolReconstructor still mix protocol + execution?

**Answer: YES (but acceptable with justification) ⚠️**

**Current responsibilities**:
- ✅ Protocol reconstruction (PendingToolCall → Spring AI Message)
- ✅ Tool execution coordination (via ToolCallingManager)

**Justification** (from T2.5A gate):
- Spring AI's ToolCallingManager requires reconstructed ChatResponse as input
- Protocol reconstruction and tool execution cannot be cleanly separated in Spring AI
- Splitting would create artificial boundary without semantic value

**Assessment**: Name is slightly misleading ("Reconstructor" suggests pure protocol), but behavior is stable and justified.

### 3. What Spring AI resumed-execution responsibilities remain in Engine?

**SpringAiToolCallingEngine currently owns**:
- Initial execution (execute method)
- Initial suspension (ephemeral + durable)
- Durable resume orchestration (resumeProcess)
- CHECK A (loadAndValidateCheckpoint)
- RuntimeBinding resolution
- Approved/rejected protocol reconstruction coordination
- Durable continuation (durableContinueWithMessages)
- CHECK B (completion + re-suspension)
- Lifecycle event emission

**Spring AI-specific concerns in Engine**:
- ChatModel, ChatMemory, ToolGovernancePolicy fields
- GovernanceToolCallingAdvisor construction
- ChatClient construction
- Spring AI Message manipulation

**R3 candidate**: Extract Spring AI resumed-execution into dedicated handler

### 4. Is source truth consistent with introducing package-private ResumedExecutionHandler next?

**Answer: YES ✅**

**Supporting evidence**:
- ProtocolReconstructor already encapsulates Spring AI tool execution
- ToolObservationContext now cleanly separates correlation from Spring AI mechanics
- reconstructAndExecuteApproved + reconstructDenialResponses + durableContinueWithMessages form a cohesive Spring AI resumed-execution unit
- CHECK A/B remain durable orchestration concerns (not Spring AI)

**No contradictions found in source truth.**

### 5. Did R2 reveal any reason to change T2.5A R3 design?

**Answer: NO - R3 design validated ✅**

**R2 confirmed**:
- Tool observation context is indeed cohesive (passes all 5 tests)
- Parameter reduction from 7 → 5 → 4 is meaningful (not just counting)
- ProtocolReconstructor ownership is correct (Spring AI integration detail)
- Checkpoint authority boundary must be protected (validated by no-SuspensionCheckpoint rule)

**R3 can proceed as designed with**:
