## 关键发现

### 发现 #1: SuspensionCheckpoint 87.5% 通用

**字段分析:**

| 类型 | 数量 | 字段 |
|------|------|------|
| **通用** | 7/8 | processId, checkpointVersion, runtimeBindingKey, sessionId, accumulatedEvidences, executionEpoch, schemaVersion |
| **特化** | 1/8 | pendingBatch |

**结论:** 泛化在技术上可行。

### 发现 #2: 只有一个经过验证的用例

**经过验证的持久化边界:**
- ✅ WAITING_FOR_APPROVAL（唯一）

**T6.1 评估但拒绝的边界:**
- ❌ ALLOW 工具执行（故意临时）
- ❌ 模型调用后（无语义价值）
- ❌ 工具批次物化后（不需要）

**结论:** 没有第二个用例需要泛化。

### 发现 #3: 过早泛化的成本

**如果现在泛化:**
- 复杂性增加（continuation type/kind, payload 抽象）
- 认知负担（用户需要理解通用模型）
- 维护负担（更多抽象层）
- **零实际价值**（没有第二个用例受益）

**YAGNI 原则:** 泛化需要 ≥2 个真实用例。

### 发现 #4: 现有机制已经通用

**已经通用的机制（50%）:**
- checkpointVersion（乐观 CAS）
- CHECK A（加载 + 验证）
- CHECK B（CAS 转换）
- RuntimeBindingResolver
- executionEpoch（重启检测）
- InvocationStateStore（T5 恢复）

**这些不需要泛化——它们已经是通用的。**

---

## 最终决策

### M6-T6.2: NO-GO（当前泛化）

**理由:**

1. **只有一个经过验证的用例**（WAITING_FOR_APPROVAL）
2. **T6.1 证明 ALLOW 是故意临时的**（无第二个边界）
3. **泛化需要 ≥2 个用例才有意义**（YAGNI 原则）
4. **特化模型对单一用例更清晰**（认知简单性）
5. **可以在未来需要时泛化**（87.5% 已通用）

### 统一约束护栏（未来）

**如果将来添加新的持久化边界，则必须:**

1. ✅ 通过泛化现有 M5/M6 模型实现
2. ✅ 重用 CheckpointStore（不创建 SemanticCheckpointStore）
3. ✅ 重用 checkpointVersion（不创建单独版本控制）
4. ✅ 重用 CHECK A/B（不创建单独协议）
5. ✅ 重用 DurableResumeCoordinator 机制
6. ✅ 重用 RuntimeBindingResolver
7. ✅ 重用 executionEpoch
8. ✅ 与 T5 组合（operationId, InvocationStateStore）

**禁止:**
- ❌ 创建并行恢复栈
- ❌ 创建第二个 current-state authority
- ❌ 创建第二个 checkpoint CAS 协议

## 最终原则

**期望的演化:**

```
SPECIAL CASE (批准暂停)
    ↓
发现通用语义（如果出现第二个用例）
    ↓
泛化现有模型
    ↓
SPECIAL CASE 仍然自然
```

**不是:**

```
SPECIAL CASE
    +
NEW GENERAL SYSTEM
    +
它们之间的适配器
```

**Arctra 应该获得更多恢复能力，同时拥有更少的概念恢复模型，而不是更多。**
