## 7. InvocationIntent 覆盖范围

**验证 M6-T4 不变式:**

> "物理调用之前必须成功提交 invocation-intent"

**测试此不变式是否适用于:**
1. ✅ Checkpoint-backed 批准恢复: **是**
2. ❌ 普通非 HITL ALLOW 执行: **否**

**源代码证据:**

```java
// SpringAiResumedExecutionHandler.executeOperations() 中:

        processId, operation.operationId(), attemptId);

    ToolResponse response = delegate.call();

```

**但在 `GovernanceToolCallingAdvisor` ALLOW 路径中:**

```java

    toolCallingManager.executeToolCalls(currentRequest.prompt(), chatResponse);
    // ^ 直接调用 Spring AI，无 intent 记录
```

**结论: ALLOW 执行绕过 InvocationStateStore。**

## 8. 对抗性场景 A: 非 HITL 崩溃后重复副作用

### 场景描述

```
execute(request: "转账 $100 给客户 123")
    ↓
模型返回: transfer(customer=123, amount=100)
    ↓
治理评估: ALLOW
    ↓
delegate.call() - 外部支付系统提交扣款
    ↓
❌ JVM 崩溃（在工具响应整合前）
```

**重启后:**

```
execute(相同业务请求: "转账 $100 给客户 123")
    ↓
模型再次返回: transfer(customer=123, amount=100)
    ↓
治理评估: ALLOW
    ↓
delegate.call() - 外部支付系统再次提交扣款
```

### 分析结果

**回答验证门控问题:**

1. **使用什么 processId?** ❌ 无 - 从不生成
2. **使用什么 operationId?** ❌ 无 - 从不生成  
3. **OP-A 可恢复吗?** ❌ 否 - 不存在
4. **OP-A 甚至可发现吗?** ❌ 否 - 未持久化
5. **分类器会运行吗?** ❌ 否 - 无 processId 触发恢复
6. **Arctra 能知道 A1 MAY_HAVE_INVOKED 吗?** ❌ 否 - 无 intent 记录
7. **Arctra 能防止第二次扣款吗?** ❌ **否**
8. **如果是，展示确切机制:** N/A
9. **如果否，明确说明重复副作用可能:** ✅ **是 - 重复副作用可能发生**

**关键结论:**

> Arctra **无法**防止普通 ALLOW 执行崩溃后的重复外部副作用。

## 10. 对抗性场景 C: 相同工具名/相同参数

### 场景描述

```
toolName = "transfer"
arguments = { customer: 123, amount: 100 }
```

两次执行，语义相同。

### 分析结果

Arctra **不应该**仅基于以下内容推断持久化身份：
- 工具名称
- 参数
- 顺序
- toolCallId（Spring AI 协议，非稳定）

**验证结果:**

当前 Arctra **不**基于语义哈希关联操作，因为：
- operationId 通过 `OperationIds.generate()` (UUID) 生成
- 不基于内容哈希
- 这是**正确的设计**（避免错误的相似性假设）

**但这意味着:**

没有其他机制可以在重启后关联"相同"的逻辑操作。

## 13. 重启重建分析

### 当前架构能否重建逻辑操作身份?

**从每个权威检查:**

| 权威 | 包含 operationId? | 包含足够的重建信息? |
|------|------------------|-------------------|
| CheckpointStore | ✅ 是（pendingBatch） | ❌ 仅批准暂停 |
| InvocationStateStore | ✅ 是（intent 记录） | ❌ 仅恢复路径 |
| ChatMemory | ❌ 否（toolCallId ≠ operationId） | ❌ 协议身份，非框架身份 |
| ExecutionLedger | ❌ 否（历史权威，非恢复） | ❌ 审计，非状态重建 |

**结论: 普通 ALLOW 执行后没有权威可以重建 operationId。**

## 14. 不要混淆 Intent 与操作物化

### 明确区分

**逻辑操作存在** (操作物化)
- 模型返回了工具调用
- Arctra 知道"应该执行 transfer(123, 100)"

VS

**物理调用意图存在** (invocation intent)
- `InvocationStateStore.recordInvocationIntent()` 成功
- Arctra 知道"允许物理尝试 A1 进行"

**当前 M6-T6 可能混淆了这些。**

`InvocationStateStore` 证明了关于物理尝试的事情。

它**不**自动证明运行时可以在崩溃后重建逻辑执行计划。

**对于 ALLOW 执行:**
- 逻辑操作物化: ✅ 发生（模型返回工具调用）
- 物理调用意图: ❌ 未记录（绕过 InvocationStateStore）

## 15. 三种契约分类

### CONTRACT A — 完全持久化执行

❌ **不适用于当前 Arctra**

**定义:**
> 每个物化的 AgentProcess 执行都可以跨崩溃安全继续，包括非 HITL ALLOW 工具执行。

**当前现实:**
- ALLOW 执行没有 AgentProcess
- 没有 processId
- 没有 operationId
- 没有 checkpoint

### CONTRACT B — 仅 Checkpoint-Backed 持久性

✅ **这是当前 Arctra 契约**

**定义:**
> 持久化恢复保证仅在 SuspensionCheckpoint 存在时开始。  
> 暂停前的普通 execute() 是临时的。  
> 崩溃 → 调用者可能重新启动请求，但框架**不**保证外部副作用去重。

**当前现实:**
- ✅ Checkpoint 存在 = 持久化恢复可用
- ✅ 无 checkpoint = 临时执行
- ✅ 外部副作用责任: 调用者

### CONTRACT C — 混合

❌ **不适用**

**为什么不是 C:**

如果声称"某些普通执行副作用通过 InvocationStateStore 是持久化/可恢复的"：

这需要证明 ALLOW 路径**使用** InvocationStateStore。

**源代码证明它不使用。**

## 16. 重新评估 T6 声明

### 原始声明

> "从头重新执行是安全的。"

### 最终结果分类

**❌ FALSE — 对于可能有外部副作用的 ALLOW 工具**

**✅ TRUE ONLY UNDER EXPLICIT PRECONDITIONS:**

1. **工具是幂等的**（应用程序保证）
2. **调用者提供业务幂等性密钥**（外部契约）
3. **无非幂等 ALLOW 工具**（应用程序设计）
4. **副作用前使用 HITL**（应用程序策略）

**这些前提条件由架构假设但不强制执行。**

## 18. 最小缺失的持久化事实

**如果我们要填补空白，缺少什么？**

**假设: 应用程序策略要求对非幂等 ALLOW 工具进行崩溃安全执行。**

**所需的新持久化事实:**

> "此逻辑操作已物化，是其物理尝试属于 OP-A 的操作"

**更精确地说:**

在非幂等物理工具调用可能发生之前：
1. 逻辑操作身份（operationId）
2. 操作上下文（processId, sessionId）  
3. 足够的继续上下文

必须已经是持久化的。

## 19. 最小解决方案选项（如果需要）

**⚠️ 注意: 这些是假设性的。决策路径可能不需要它们。**

### 选项 1: 在物理调用前持久化逻辑操作物化

**What:**
- 治理返回 ALLOW 后，立即持久化 PendingToolCall
- 在执行前创建 processId + operationId

**Pros:**
- 逻辑操作身份存活崩溃
- 恢复可以查询 InvocationStateStore

**Cons:**
- ALLOW 快速路径的写入开销
- 需要为"操作已物化但未暂停"创建持久化状态
- 新的崩溃窗口（操作持久化 vs ChatMemory）

### 选项 2: 在副作用能力 ALLOW 工具前物化持久化 AgentProcess

**What:**
- 检测工具是否有副作用风险
- 在执行前创建临时 checkpoint

**Cons:**
- 需要工具风险分类（新治理契约）
- 复杂性高
- 可能误分类工具

### 选项 3: 要求应用程序为不安全 ALLOW 工具提供幂等性身份

**What:**
- 应用程序在工具参数中提供业务幂等性密钥
- Arctra 基于此密钥去重

**Cons:**
- 将责任转移到应用程序
- 需要新的公共 API 契约
- 无法对遗留工具强制执行

### 选项 4: 通过持久化执行边界路由副作用能力工具

**What:**
- 治理检测副作用工具
- 自动路由到 REQUIRE_APPROVAL（强制 checkpoint 创建）

**Cons:**
- 改变治理语义（ALLOW 变为 REQUIRE_APPROVAL）
- 用户体验影响
- 可能不受欢迎

### 选项 5: 接受临时性（当前设计）

**What:**
- 明确记录 ALLOW = ephemeral
- 应用程序对外部副作用去重负责

**Pros:**
- 零实现
- 诚实的契约
- 与当前行为一致

**Cons:**
- 无框架级崩溃安全
- 依赖应用程序纪律

## 20. 持久性契约分类

**基于源代码真相，Arctra 的实际契约是:**

### CONTRACT B — CHECKPOINT-BOUNDED DURABILITY

**定义:**

```
AgentRuntime.execute()
= 临时执行，除非持久化暂停物化

resumeProcess(...)
= checkpoint-backed 持久化执行
```

**适用边界:**

| API | 持久性保证 | 恢复能力 | 副作用保护 |
|-----|----------|---------|-----------|
| `execute()` ALLOW | ❌ 临时 | ❌ 无 | ❌ 无 |
| `execute()` → suspend | ✅ 持久化 | ✅ 恢复 | ⚠️ 批准前 |
| `resumeProcess()` | ✅ 持久化 | ✅ 完整恢复 | ✅ T5 分类 |

**外部副作用责任:**

对于 **ALLOW 路径**:
- Arctra: 尽力而为执行，无崩溃恢复
- 应用程序: 负责幂等性/去重

对于 **HITL 路径**:
- Arctra: 跨 JVM 边界的完整恢复
- 应用程序: 提供批准决策

M6 提供:

- ❌ 临时 ALLOW 执行的恢复语义

## 22. 最终决策

## ✅ RESULT B — CONDITIONAL GO: M6 持久性契约是 CHECKPOINT-BOUNDED

### 含义

1. **普通 ALLOW 执行是故意临时的**
   - 无 processId
   - 无 operationId
   - 无 checkpoint
   - 无 InvocationStateStore 覆盖

2. **Checkpoint-backed 执行是持久化的**
   - 完整的恢复权威
   - T5 分类和解析
   - 跨 JVM 边界安全

3. **文档/API 契约必须明确说明这一点**
   - 澄清持久性边界
   - 纠正误导性声明
   - 明确外部副作用责任

4. **无需实施通用 checkpoint**
   - 当前设计是故意的
   - 不是架构疏忽
   - 临时性是可接受的权衡

### M6-T6 NO-GO 状态

**✅ M6-T6 NO-GO 保持有效**

**但澄清原因:**

**旧理由（不准确）:**
> "从头重新执行是安全的，因为工具恢复由 InvocationStateStore 处理"

**新理由（准确）:**
> "普通执行是故意临时的。Checkpoint-backed 执行是持久化的。这种双重契约是正确的设计选择，反映了自然的持久性边界（批准决策点）。"
