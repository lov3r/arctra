**任务:** M6-T6.2 Mandatory Architecture Constraint  
**优先级:** CRITICAL

## 执行摘要

**中心架构问题:**

> 现有的 suspension/resume 机制是否已经是一个更通用的持久化语义继续模型的特化形式？

**分析结果:**

✅ **YES — 但泛化目前不合理**

**最终决策:**

**NO-GO: 不泛化 SuspensionCheckpoint（当前）**

**理由:**
1. **T6.1 证明了 ALLOW 执行是故意临时的**
2. **批准暂停是唯一经过验证的持久化边界**
3. **没有第二个经过验证的语义继续状态需要持久化**
4. **泛化需要至少两个真实用例才有意义**
5. **过早泛化会创造不必要的抽象复杂性**

**关键洞察:**

> 统一约束不意味着必须立即泛化。
> 
> 当只有一个用例时，保持特化模型更清晰。
> 
> 统一约束是为未来设定的护栏：**如果**添加新的持久化边界，**则**必须通过泛化现有模型实现，而不是创建并行栈。

**问题 A — 粒度:**
> 哪些语义边界应该是持久化的？

**问题 B — 统一:**
> 这些边界如何成为现有 suspension/resume 恢复模型的一部分，而不创建并行恢复架构？

### 假设：批准暂停是一种持久化语义继续

**概念模型:**

    ├── READY_FOR_TOOL_EXECUTION (假设的)
    │   └── payload: ??? (未定义)
    │
    └── READY_FOR_MODEL_CONTINUATION (假设的)
        └── payload: ??? (未定义)

### 评估结果

**问题 1: 有多少个经过验证的继续状态？**

✅ **ONE: WAITING_FOR_APPROVAL**

**问题 2: T6.1 是否验证了第二个状态的需求？**

❌ **NO**

- ALLOW 执行是**故意临时的**

**问题 3: 是否存在其他经过验证的语义继续需求？**

❌ **NO**

- 经过验证的非 HITL 持久化需求

- 证明其他语义边界价值的真实用例

**泛化需要至少两个真实用例。**

## 5. 泛化时机分析

### YAGNI 原则（You Aren't Gonna Need It）

**问题:** 何时应该泛化抽象？

**答案:** 当至少有两个真实用例，并且它们共享足够的语义相似性时。

### 当前状态

| 标准 | 当前 | 需要 |
|------|------|------|
| 验证的用例数 | 1 | ≥ 2 |
| 共享语义 | N/A | 清晰 |
| 应用程序需求 | 无 | 明确 |
| 架构价值 | 假设的 | 证明的 |

**结论: 泛化时机未到。**

### 过早泛化的成本

**如果现在泛化 SuspensionCheckpoint：**

1. **复杂性增加**
   - 引入 continuation type/kind 概念
   - 引入 payload 抽象
   - 可能的 sealed interface / ADT
   - 增加的测试矩阵

2. **认知负担**
   - 用户需要理解通用模型
   - 当只有一个用例时，特化模型更清晰
   - 文档复杂性

3. **维护负担**
   - 更多的抽象层
   - 更难调试
   - 更难演化

4. **零实际价值**
   - 没有第二个用例受益
   - 没有应用程序使用新能力
   - 纯粹的"以防万一"抽象

### 推荐方法

**现在:**
- 保持 SuspensionCheckpoint 特化
- 记录泛化假设（用于未来）
- 建立统一约束护栏

**未来（如果需要）:**
- 当第二个真实用例出现时
- 评估共享语义
- 最小化泛化现有模型
- 重用 CHECK A/B, binding, epoch, T5

## 6. 统一约束护栏

### 如果将来添加新的持久化边界

**统一约束要求:**

1. **必须重用 CheckpointStore（或泛化）**
   - 不创建 SemanticCheckpointStore
   - 单一当前状态权威

2. **必须重用 checkpointVersion 语义**
   - 不创建单独的版本控制
   - 单一乐观 CAS 模型

3. **必须重用 CHECK A**
   - 不创建单独的加载/验证
   - 单一恢复入口点

4. **必须重用 CHECK B**
   - 不创建单独的 CAS 协议
   - replaceIfVersion / deleteIfVersion 足够

5. **必须重用 DurableResumeCoordinator 机制**
   - 不创建 SemanticRecoveryCoordinator
   - 扩展现有编排逻辑

6. **必须重用 RuntimeBindingResolver**
   - 所有继续通过相同绑定机制
   - 不创建并行绑定模型

7. **必须重用 executionEpoch**
   - 所有继续使用相同重启检测
   - 不创建单独的 epoch

8. **必须与 T5 组合**
   - operationId 保持稳定
   - InvocationStateStore 重用
   - 恢复分类重用

### 架构成功标准

**如果将来泛化，必须能够说:**

> Arctra 有**一个**持久化继续模型。
> 
> 批准暂停是**一种**继续状态。
> 
> 崩溃恢复从选定的语义边界使用**相同的**状态权威、世代/CAS 模型、运行时绑定解析、重启检测和工具恢复机制。
> 
> 不同的继续状态可能携带不同的最小语义载荷，但它们不创建单独的恢复栈。

- SuspensionCheckpoint 直接表示批准暂停
- 没有适配器层

**这表明:** 架构是正确的特化，而非错误的通用化。

## 9. 问题 B 答案：如何统一？

### 当只有一个用例时

**答案:** 不泛化。保持特化。

**理由:**
- 泛化需要 ≥2 个用例才有意义
- 特化模型对单一用例更清晰
- 过早抽象增加复杂性而无价值
- 可以在未来需要时泛化

### 统一约束的真正含义

**统一约束不是:**
- "立即泛化所有东西"
- "创建抽象以防万一"
- "预测所有未来用例"

**统一约束是:**
- "如果添加新边界，通过泛化现有模型实现"
- "不创建并行恢复栈"
- "重用 CHECK A/B, binding, epoch, T5"

**这是一个护栏，而不是行动命令。**

## 25. 最终原则

**期望的演化是:**

```
SPECIAL CASE (批准暂停)
    ↓
发现通用语义（如果出现第二个用例）
    ↓
泛化现有模型
    ↓
SPECIAL CASE 仍然自然
```

**不是:**

```
SPECIAL CASE
    +
NEW GENERAL SYSTEM
    +
它们之间的适配器
```

**Arctra 应该获得更多恢复能力，同时拥有**更少**的概念恢复模型，而不是更多。**

## 26. 架构成功标准（未来）

**如果将来泛化，必须能够说:**

> Arctra 有**一个**持久化继续模型。
> 
> 批准暂停是**一种**继续状态。
> 
> 崩溃恢复从选定的语义边界使用**相同的**状态权威、世代/CAS 模型、运行时绑定解析、重启检测和工具恢复机制。
> 
> 不同的继续状态可能携带不同的最小语义载荷，但它们不创建单独的恢复栈。

**当前:** 这个标准是**假设的**（只有一个用例）。

**未来:** 如果添加新边界，这个标准变为**要求**。
