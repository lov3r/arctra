# M6-T6.3 双模式执行架构门控
## EPHEMERAL + DURABLE 统一模型

**任务:** M6-T6.3 Architecture Gate  
**类型:** ARCHITECTURE GATE (无实现代码)  
**优先级:** CRITICAL  
**日期:** 2025-09-16  
**状态:** 分析中

## 执行摘要

### 产品需求变化

M6-T6.2 的前提已失效：

**旧前提（M6-T6.2）:**
> 只有一个经过验证的持久化用例: WAITING_FOR_APPROVAL

**新产品需求（M6-T6.3）:**

Arctra **必须**同时支持非 HITL ALLOW 执行的两种模式:

1. **EPHEMERAL 模式** - 轻量级、快速路径、无持久化
2. **DURABLE 模式** - 语义进度跨 JVM 边界持久化

### 中心架构问题

> 如何让 Arctra 支持 DURABLE 非 HITL 自动执行，
> 通过**最小化泛化**现有 M5/M6 suspension/resume 模型实现，
> 同时保留现有的 EPHEMERAL ALLOW 快速路径？

### 关键要求

**必须分离三个正交关注点:**

1. **治理 (Governance)** - 操作是否被允许执行？
2. **持久性 (Durability)** - 接受的语义进度是否必须跨故障存活？
3. **继续倾向 (Continuation Disposition)** - 执行能否自动继续、必须等待外部输入、还是已完成？

**必须重用现有恢复脊柱:**

- 一个当前状态权威 (CheckpointStore)
- 一个 CAS 模型 (checkpointVersion)
- 一个运行时绑定机制 (RuntimeBindingResolver)
- 一个重启检测 (executionEpoch)
- 一个物理尝试恢复权威 (T5 InvocationStateStore)

**禁止创建:**

- 第二个恢复栈
- 第二个当前状态权威
- 第二个 CAS 协议
- 并行的恢复协调器

## 1. 更新的产品需求

### 1.1 有效用例矩阵

| 治理 | 持久性 | 继续倾向 | 有效? | 用例 |
|-----|-------|---------|------|-----|
| ALLOW | EPHEMERAL | RUNNABLE | ✅ | 当前默认快速路径 |
| ALLOW | DURABLE | RUNNABLE | ✅ | **新需求** - 长时间运行的自动执行 |
| REQUIRE_APPROVAL | DURABLE | WAITING | ✅ | M5/M6 已验证 |
| REQUIRE_APPROVAL | EPHEMERAL | WAITING | ❓ | 语义上矛盾（等待外部信号需要持久化） |
| REJECT | * | TERMINAL | ✅ | 治理拒绝（持久性无关） |

**关键洞察:**

```
治理决策 ≠ 持久性选择
批准要求 → 自然升级到持久化（等待外部信号）
ALLOW → 可以是 EPHEMERAL 或 DURABLE（应用程序选择）
```

### 1.2 为什么 T6.2 前提不再有效

T6.2 结论基于:
> "只有一个真实的持久化继续用例: WAITING_FOR_APPROVAL"

现在产品明确要求:

**用例 #1 (已验证):**
```
REQUIRE_APPROVAL
+ DURABLE
+ WAITING_FOR_EXTERNAL_SIGNAL
```

**用例 #2 (新需求):**
```
ALLOW
+ DURABLE
+ AUTOMATIC_CONTINUATION
```

**因此:** 不能再说"只有一个用例"来拒绝泛化。

## 2. 现有恢复脊柱审计

### 2.1 源代码真相（当前实现）

**核心组件清单:**

| 组件 | 位置 | 职责 |
|-----|------|------|
| `SuspensionCheckpoint` | arctra-core | 持久化继续状态 |
| `CheckpointStore` | arctra-core | 当前状态权威 (CRUD + CAS) |
| `checkpointVersion` | SuspensionCheckpoint | 乐观锁世代 |
| `RuntimeBinding` | arctra-core | 恢复时的 (definition, context) |
| `RuntimeBindingResolver` | arctra-core | 绑定解析契约 |
| `DurableExecutionEngine` | arctra-core | 持久化能力接口 |
| `DurableResumeCoordinator` | arctra-runtime-react | 恢复编排器 |
| `InvocationStateStore` | arctra-runtime-react | T5 物理尝试权威 |
| `InvocationRecoveryClassifier` | arctra-runtime-react | T5 恢复分类 |
| `executionEpoch` | SuspensionCheckpoint | M6-T4F 重启检测 |
| `SpringAiToolCallingEngine` | arctra-runtime-react | 持久化引擎实现 |
| `ResumedExecutionHandler` | arctra-runtime-react | 协议重建 + 执行 |

### 2.2 现有恢复脊柱流程

```
用户/应用程序
    ↓
resumeProcess(processId, checkpointVersion, signal)
    ↓
DurableExecutionEngine.resumeProcess(...)
    ↓
DurableResumeCoordinator.resume(...)
    ↓
CHECK A: loadAndValidateCheckpoint()
    ├─ load(processId)
    └─ validate checkpointVersion
    ↓
executionEpoch 比较 (M6-T4F)
    ↓
    ├─ same incarnation → 正常恢复路径
    │   ├─ zero recovery classification
    │   ├─ resumeNormalInternal()
    │   └─ → TOOL EXECUTION
    │
    └─ cross-incarnation → 恢复分类路径
        ├─ InvocationRecoveryClassifier.classify()
        ├─ preflight: fail-closed on MAY_HAVE_INVOKED
        ├─ resumeWithRecoveryInternal()
        └─ → TOOL EXECUTION (if safe)
    ↓
RuntimeBindingResolver.resolve(runtimeBindingKey)
    ↓
RuntimeBinding(definition, context)
    ↓
validateAndEmitApproval(signal)
    ↓
ResumedExecutionHandler.executeResume(...)
    ├─ 协议重建 (Spring AI messages)
    ├─ 工具执行 (with T5 invocation intent)
    ├─ 模型继续
    └─ → ResumedExecutionOutcome
    ↓
handleResumedExecutionOutcome(...)
    ↓
    ├─ ModelCompleted → CHECK B: deleteIfVersion()
    │   ├─ CAS success → COMPLETED
    │   └─ CAS fail → CheckpointTransitionConflictException
    │
    └─ GovernanceSuspended → CHECK B: replaceIfVersion()
        ├─ CAS success → SUSPENDED (v+1)
        └─ CAS fail → CheckpointTransitionConflictException
```

**关键发现:**

1. **CHECK A 是通用的** - 加载 + 验证 checkpoint
2. **CHECK B 是通用的** - CAS 条件转换
3. **executionEpoch 是通用的** - 重启检测
4. **RuntimeBinding 是通用的** - 恢复绑定
5. **T5 recovery 是通用的** - 物理尝试恢复
6. **批准特定的** - ContinuationSignal.ApprovalSignal

**字段分类:**

|------|-------------|---------|---------|
| schemaVersion | ✅ | ❌ | ❌ |
| processId | ✅ | ❌ | ❌ |
| checkpointVersion | ✅ | ❌ | ❌ |
| runtimeBindingKey | ✅ | ❌ | ❌ |
| sessionId | ✅ | ❌ | ❌ |

## 3. 三个正交关注点分离

### 3.1 治理 (Governance)

**概念模型:**
```
ALLOW            - 操作被允许立即执行
REQUIRE_APPROVAL - 操作需要外部批准
REJECT           - 操作被拒绝
```

**回答的问题:**
> "这个操作现在可以执行吗？"

**当前实现:**
- `ToolGovernancePolicy.evaluateBatch()`
- `GovernanceToolCallingAdvisor`
- `ContinuationSignal.ApprovalSignal`

**关键:** 治理决策不应隐式确定持久性。

### 3.2 持久性 (Durability)

**概念模型:**
```
EPHEMERAL - 语义进度不跨 JVM 边界存活
DURABLE   - 接受的语义进度必须跨故障存活
```

**回答的问题:**
> "接受的语义执行进度必须跨 JVM/进程故障存活吗？"

**当前实现:**
- EPHEMERAL: 不创建 processId、不持久化 checkpoint
- DURABLE: 创建 processId、持久化 checkpoint (仅在 REQUIRE_APPROVAL 时)

**新需求:** ALLOW + DURABLE 必须成为可能。

### 3.3 继续倾向 (Continuation Disposition)

**概念模型:**
```
RUNNABLE              - 执行可以自动继续
WAITING_FOR_SIGNAL    - 必须等待外部输入才能继续
COMPLETED             - 执行已完成
```

**回答的问题:**
> "执行能否自动继续、必须等待外部输入、还是已完成？"

**当前实现:**
- WAITING_FOR_SIGNAL: SuspensionCheckpoint 存在 + WAITING status
- COMPLETED: checkpoint 被删除

**新需求:** DURABLE RUNNABLE 必须成为可能（自动继续）。

### 3.4 正交性验证

**有效组合示例:**

| 治理 | 持久性 | 继续倾向 | 语义 |
|-----|-------|---------|------|
| ALLOW | EPHEMERAL | RUNNABLE | 当前默认快速路径 |
| ALLOW | DURABLE | RUNNABLE | 长时间运行自动执行（新） |
| REQUIRE_APPROVAL | DURABLE | WAITING | M5/M6 已验证 |
| REJECT | * | TERMINAL | 治理拒绝 |

**无效组合示例:**

| 治理 | 持久性 | 继续倾向 | 为什么无效？ |
|-----|-------|---------|-----------|
| REQUIRE_APPROVAL | EPHEMERAL | WAITING | 等待外部信号需要持久化 |

**关键洞察:**

```
REQUIRE_APPROVAL 自然升级到 DURABLE
（等待外部信号不能是 JVM-local）

但 ALLOW 可以是:
  - EPHEMERAL (轻量级、快速)
  - DURABLE (长时间运行、可恢复)
```

## 4. ALLOW + DURABLE 语义分析

### 4.1 最小持久化不变式

**候选不变式:**

> 对于 DURABLE 执行：
> 
> 一旦 Arctra 接受一个逻辑操作用于 DURABLE 执行
> 并分配了 operationId，
> 该逻辑操作必须在物理副作用能力调用被允许之前
> 成为持久化可达的。

**概念上:**

```
模型语义决策
    ↓
接受的逻辑操作 OP-A
    ↓
DURABLE COMMIT (checkpoint)
    ↓
尝试 A1 被允许
    ↓
InvocationStateStore intent
    ↓
delegate.call()
```

**崩溃后:**

```
加载持久化继续
    ↓
恢复 OP-A (从 checkpoint.pendingBatch)
    ↓
findAttempts(OP-A)
    ↓
恢复/分类 A1
    ↓
T5 语义继续
```

**关键问题:**

1. 逻辑操作在哪里物化？
2. operationId 何时分配？
3. 第一个持久化边界在哪里？
4. 工具结果如何持久化？
5. 模型继续如何重建？

### 4.2 第一个持久化语义边界

**候选边界:**

**选项 A: TOOL_BATCH_MATERIALIZED**

```
模型返回 tool calls
    ↓
Arctra 分配 operationId (每个工具)
    ↓
构建 PendingToolCall 列表
    ↓
DURABLE COMMIT checkpoint
    ├─ processId
    ├─ checkpointVersion: 1
    ├─ pendingBatch: [op-1, op-2, ...]
    └─ executionEpoch
    ↓
自动继续（无需外部信号）
    ↓
对每个操作:
    ├─ recordInvocationIntent(proc, opId, attemptId)
    ├─ delegate.call()
    └─ 收集结果
    ↓
构建继续输入
    ↓
CRASH 可能点
    ↓
重启后:
    ├─ load checkpoint
    ├─ 恢复 pendingBatch
    ├─ 对每个操作分类
    │   ├─ DEFINITELY_NOT_DISPATCHED → 执行
    │   ├─ MAY_HAVE_INVOKED → 操作员解析
    │   ├─ RESOLVED_EXECUTED → 使用恢复的结果
    │   └─ RESOLVED_NOT_EXECUTED → 新尝试
    ├─ 重建继续
    └─ 模型继续
```

**优点:**
- operationId 在物理调用前持久化
- T5 恢复分类自然工作
- 与现有 suspension 模型语义接近
- 清晰的第一个语义边界

**缺点:**
- 每个工具批次需要 checkpoint write
- 相对于 EPHEMERAL 有持久化开销

**选项 B: 工具执行后持久化**

```
模型返回 tool calls
    ↓
立即执行工具 (无持久化)
    ↓
收集结果
    ↓
DURABLE COMMIT
    ├─ 工具结果
    └─ 继续状态
    ↓
模型继续
```

**缺点:**
- 工具可能在持久化前执行（副作用风险）
- operationId 可能无法跨崩溃存活
- T5 恢复无法重连未持久化的操作
- **违反了候选不变式**

**推荐: 选项 A (TOOL_BATCH_MATERIALIZED)**

理由:
1. 保持 T5 恢复语义完整
2. operationId 在副作用前持久化
3. 与现有 suspension 边界一致
4. 支持跨崩溃的精确恢复分类

### 4.3 工具结果持久性

**问题:** 工具执行后崩溃如何恢复？

**当前权威清单:**

| 权威 | 拥有什么 | 不拥有什么 |
|------|---------|-----------|
| CheckpointStore | 当前继续状态 | 工具结果 |
| InvocationStateStore | 尝试 intent + resolution | 工具结果详情 |
| ChatMemory | 会话历史 | 恢复权威 |
| ExecutionLedger | 历史事实 | 当前状态 |
| Evidence | 执行证据/内容 | 持久化 |

**选项比较:**

**选项 1: InvocationStateStore 存储结果**

```java
recordResolution(processId, opId, attemptId, EXECUTED, recoveredResult)
```

当前 T5 已支持。

**优点:**
- 已有基础设施
- 与恢复分类集成
- 可以跨崩溃恢复工具结果

**缺点:**
- InvocationStateStore 不应成为通用结果缓存
- 结果可能很大

**选项 2: 工具结果在新 checkpoint 中**

```
工具批次执行
    ↓
收集结果
    ↓
CHECK B: replaceIfVersion(v1, v2)
    ├─ completedOperations: [...]
    └─ 继续输入
```

**优点:**
- 当前继续状态包含所有需要的数据
- 不扩展 InvocationStateStore 职责

**缺点:**
- checkpoint payload 膨胀
- 每批次工具需要 checkpoint write

**选项 3: 无工具结果持久化（重新执行）**

崩溃后重新执行工具。

**缺点:**
- 副作用可能重复
- 非幂等工具有风险
- 与 T5 at-least-once 语义冲突

**推荐: 选项 1 + 2 混合**

- 使用 InvocationStateStore resolution 作为恢复分类的真相源
- 对 RESOLVED_EXECUTED 操作，从 resolution 重建工具结果
- 不在 checkpoint 中存储详细工具结果
- 支持 T5 操作员驱动的解析

### 4.4 模型继续重建

**问题:** 工具结果可用后如何继续模型？

当前 `ResumedExecutionHandler` 已知如何:

```java
ResumedExecutionOutcome executeResume(
    List<PendingToolCall> pendingBatch,
    RuntimeBinding binding,
    List<Evidence> historicalEvidences,
    ContinuationSignal signal,
    ToolObservationContext observationContext,
    List<RecoveryClassificationResult> classifications // M6-T5
)
```

**它可以:**

1. 重建 Spring AI 协议 messages
2. 处理 RESOLVED_EXECUTED (使用恢复的结果)
3. 处理 RESOLVED_NOT_EXECUTED (创建新尝试)
4. 执行工具
5. 构建 ToolResponseMessage
6. 继续模型

**对 DURABLE ALLOW:**

- 使用相同的 handler
- 无需 ApprovalSignal (自动 approved)
- classifications 包含恢复状态
- 正常工具执行路径

**结论: 现有机制足够。**

## 5. EPHEMERAL 快速路径保留

### 5.1 当前 EPHEMERAL 行为

```
ALLOW + EPHEMERAL 执行:
    ↓
无 processId 创建
无 checkpoint 写入
无 executionEpoch
无 CAS 操作
无 InvocationStateStore 写入
    ↓
直接工具执行
    ↓
模型继续
    ↓
完成
```

**性能特征:**
- 零持久化开销
- 简单的内存中执行
- 当前默认路径

### 5.2 DURABLE 模式持久化开销

**每次 DURABLE 执行估算:**

假设: 20 模型继续, 30 工具操作, 10 工具批次

**持久化写入:**

1. **初始 checkpoint 创建** - 1 write
2. **每批次工具:**
   - InvocationIntent 写入: 每操作 1 write = 30 writes
   - (可选) resolution 写入: 每操作 1 write = 30 writes
3. **每批次边界:** (如果有多个语义边界)
   - Checkpoint replace: 10 writes
4. **完成:** Checkpoint delete: 1 write

**总计:** 约 72 writes

**与 LLM 延迟比较:**

| 操作 | 延迟 |
|-----|------|
| 模型调用 | 1-10 秒 |
| 工具执行 | 100ms - 5秒 |
| 数据库写入 | 5-50ms |
| 数据库 CAS | 10-100ms |

**结论:** 
- 持久化开销相对于 LLM/工具延迟是合理的
- 但仍然是**有意义的成本**
- EPHEMERAL 作为轻量级路径仍然有价值

### 5.3 保留 EPHEMERAL 的要求

**必须避免:**

```java
// ❌ 错误 - 每次执行都持久化
execute(...) {
    if (isDurableMode()) {
        createCheckpoint();  // 即使 EPHEMERAL 也执行
    }
    // ...
}
```

**正确方法:**

```java
// ✅ 正确 - 持久性是明确选择的
execute(..., executionOptions) {
    if (executionOptions.durability() == DURABLE) {
        createCheckpoint();
    } else {
        // EPHEMERAL - 无持久化
    }
    // ...
}
```

**架构原则:**

```
EPHEMERAL 是默认的
DURABLE 是显式选择的
选择机制必须零成本（对 EPHEMERAL）
```

## 6. 持久性选择权威

### 6.1 谁拥有持久性决策？

**选项 A: AgentDefinition 级别**

```java
AgentDefinition(
    String name,
    String description,
    DurabilityMode durability  // EPHEMERAL / DURABLE
)
```

**优点:**
- Agent 类型的内在属性
- 简单配置
- 跨执行一致

**缺点:**
- 不够灵活（同一 agent 可能需要两种模式）
- API 变更

**选项 B: 执行级别（请求）**

```java
AgentExecutionContext(
    String sessionId,
    DurabilityMode durability  // EPHEMERAL / DURABLE
)
```

**优点:**
- 每请求控制
- 最大灵活性
- 明确的执行语义

**缺点:**
- 用户必须每次指定
- 可能忘记设置

**选项 C: 运行时策略**

```java
AgentRuntimePolicy {
    DurabilityMode selectDurability(
        AgentDefinition definition,
        AgentRequest request,
        AgentExecutionContext context
    );
}
```

**优点:**
- 集中策略
- 可以基于复杂逻辑

**缺点:**
- 间接性
- 可能过度设计

**选项 D: 动态升级**

```
执行开始为 EPHEMERAL
    ↓
到达重要边界
    ↓
升级到 DURABLE
    ↓
持久化继续
```

**优点:**
- 按需持久化
- 避免不必要的写入

**缺点:**
- 复杂的状态转换
- 早期工作仍然不可恢复
- 不清楚的契约

### 6.2 推荐方案

**推荐: 选项 B (执行级别) + 隐式升级**

```java
// 公共 API
AgentExecutionContext.withDurability(String sessionId, DurabilityMode mode)

// 默认
AgentExecutionContext.withSession(String sessionId)  // EPHEMERAL 默认

// 显式 DURABLE
AgentExecutionContext.durableSession(String sessionId)
```

**升级规则:**

```
REQUIRE_APPROVAL 自动升级到 DURABLE
（无论初始设置）

理由: 等待外部信号需要跨 JVM 边界持久化
```

**优点:**
- 用户明确选择
- 简单的 API
- 支持批准的自然升级
- 向后兼容 (默认 EPHEMERAL)

### 6.3 持久性契约定义

**EPHEMERAL 契约:**

```
什么存活:
- 无（崩溃后一切丢失）

什么不存活:
- processId
- 逻辑操作身份
- 工具执行状态
- 会话状态（除非 ChatMemory 持久化）

责任:
- 应用程序负责幂等性
- 应用程序负责副作用协调
- 崩溃后可能重新开始
```

**DURABLE 契约:**

```
什么存活:
- processId (稳定进程标识)
- checkpointVersion (CAS 世代)
- 逻辑操作身份 (operationId)
- pending工具批次
- 累积证据
- executionEpoch (重启检测)

什么保证:
- 逻辑操作可达性（从 checkpoint）
- T5 at-least-once 物理尝试语义
- 跨 JVM 边界恢复
- 操作员驱动的不确定性解析

什么不保证:
- Exactly-once 工具执行
- Exactly-once 模型调用
- Checkpoint/ChatMemory 原子性
- 外部副作用的 exactly-once
```

## 7. CHECK A/B 泛化

### 7.1 CHECK A 当前职责

```java
// DurableResumeCoordinator.loadAndValidateCheckpoint()
SuspensionCheckpoint loadAndValidateCheckpoint(
    String processId,
    long requestedVersion
) {
    SuspensionCheckpoint checkpoint = checkpointStore
        .load(processId)
        .orElseThrow(() -> new CheckpointNotFoundException(...));
    
    if (checkpoint.checkpointVersion() != requestedVersion) {
        throw new StaleCheckpointException(...);
    }
    
    return checkpoint;
}
```

**当前已经是通用的:**
- 加载当前 checkpoint
- 验证 generation (fencing token)
- 无批准特定逻辑

### 7.2 CHECK A 对 DURABLE ALLOW

**相同的逻辑:**

```
WAITING_FOR_APPROVAL 恢复:
    CHECK A: load + validate
    
DURABLE ALLOW 恢复:
    CHECK A: load + validate  // 完全相同
```

**无需修改。**

### 7.3 CHECK B 当前职责

```java
// 完成路径
boolean deleted = checkpointStore.deleteIfVersion(
    checkpoint.processId(),
    checkpoint.checkpointVersion()
);

// 重新悬挂路径
boolean replaced = checkpointStore.replaceIfVersion(
    oldCheckpoint.processId(),
    oldCheckpoint.checkpointVersion(),
    nextCheckpoint
);
```

**当前已经是通用的:**
- 条件 CAS 转换
- 无批准特定逻辑

### 7.4 CHECK B 对 DURABLE ALLOW

**完成路径:**

```
DURABLE ALLOW 执行完成:
    ↓
CHECK B: deleteIfVersion(processId, version)
    ↓
如果成功: checkpoint 删除
如果失败: CheckpointTransitionConflictException
```

**继续路径 (如果有多个边界):**

```
DURABLE ALLOW 工具批次完成:
    ↓
需要继续到下一个模型调用:
    ↓
CHECK B: replaceIfVersion(processId, oldVersion, nextCheckpoint)
    ├─ nextCheckpoint.checkpointVersion = oldVersion + 1
    ├─ 可能不同的 pendingBatch
    └─ executionEpoch 保留（同一 incarnation）
```

**关键:** CHECK B 语义对 WAITING 和 RUNNABLE 完全相同。

**无需修改。**

## 8. DurableResumeCoordinator 职责分析

### 8.1 当前职责（从源代码）

```java
/**
 * DurableResumeCoordinator 职责:
 * 
 * - CHECK A: checkpoint 加载和版本验证
 * - RuntimeBinding 解析
 * - ContinuationSignal 验证
 * - APPROVAL_GRANTED / APPROVAL_REJECTED 事件发射
 * - RESUMED 事件发射
 * - 恢复执行委托给 provider handler
 * - CHECK B 完成: deleteIfVersion
 * - CHECK B 重新悬挂: replaceIfVersion
 * - CHECKPOINT_CONFLICT 事件发射
 * - COMPLETED 事件发射
 * - APPROVAL_REQUIRED 事件发射
 * - SUSPENDED 事件发射
 * - 下一个 checkpoint 构建
 * - AgentProcess 物化
 */
```

### 8.2 批准特定 vs. 通用继续

**批准特定:**
```java
validateAndEmitApproval(processId, checkpointVersion, signal)
// 假设: signal instanceof ContinuationSignal.ApprovalSignal
```

**可以泛化为:**
```java
validateAndEmitContinuation(processId, checkpointVersion, signal)
// 支持:
// - ApprovalSignal (现有)
// - AutomaticSignal (新 - 对 DURABLE ALLOW)
// - 或: 简化为无外部信号的自动继续
```

### 8.3 自动继续 vs. 批准继续

**批准继续 (现有):**
```
用户调用: resumeProcess(processId, version, APPROVE)
    ↓
CHECK A
    ↓
验证 ApprovalSignal
    ↓
发射 APPROVAL_GRANTED
    ↓
执行工具
    ↓
CHECK B
```

**自动继续 (新):**
```
系统/调度器触发: resumeDurableProcess(processId, version)
    ↓
CHECK A
    ↓
无外部信号（自动批准）
    ↓
发射 RESUMED（无批准事件）
    ↓
执行工具
    ↓
CHECK B
```

**关键差异:**

| 方面 | 批准继续 | 自动继续 |
|-----|---------|---------|
| 外部信号 | ApprovalSignal | 无（或 AutomaticSignal） |
| 触发器 | 用户/操作员 | 系统/调度器/恢复 |
| 事件 | APPROVAL_GRANTED | RESUMED（无批准） |
| 等待语义 | WAITING_FOR_SIGNAL | RUNNABLE |

### 8.4 推荐泛化

**选项 A: 扩展 ContinuationSignal**

```java
sealed interface ContinuationSignal {
    record ApprovalSignal(boolean approved) implements ContinuationSignal {}
    record AutomaticSignal() implements ContinuationSignal {}  // 新
}
```

**选项 B: 可选信号**

```java
// resumeProcess 对批准（需要信号）
AgentResult resumeProcess(
    String processId,
    long checkpointVersion,
    ContinuationSignal signal  // 非 null

// resumeDurableProcess 对自动（无信号）
AgentResult resumeDurableProcess(
    String processId,
    long checkpointVersion

```

**推荐: 选项 B**

理由:
- 更清晰的 API 分离
- 避免"假"ApprovalSignal
- 不同的继续语义有不同的入口点
- 向后兼容

### 10.2 选项 A: 双栈（拒绝）

```

    SuspensionCheckpoint
    CheckpointStore
```

- 维护负担

### 10.3 选项 B: 最小泛化 SuspensionCheckpoint（推荐）

```
批准悬挂 = 等待的持久化继续

DURABLE ALLOW = 可运行的持久化继续

共享:
- CheckpointStore (当前状态权威)

- CHECK A/B
- RuntimeBinding
- executionEpoch
- T5 InvocationStateStore
```

**优点:**
- 单一恢复脊柱
- 最小架构变更
- 现有机制 87.5% 已经通用
- 清晰的迁移路径

**缺点:**
- 需要泛化 SuspensionCheckpoint 语义

### 10.4 选项 C: 启动时进程物化

```
    ├─ processId
    ├─ checkpointVersion: 1
    ├─ initialState
    └─ executionEpoch
    ↓
执行
    ↓
语义边界
    ↓
```

**优点:**

**缺点:**
- 即使零工具也写入 checkpoint
- EPHEMERAL 模式不能动态升级
- 写入放大

### 10.5 选项 D: 惰性语义物化

```
DURABLE 选择
    ↓

    ↓
到达第一个语义边界
    ↓

    ↓
继续执行
```

**优点:**
- 避免不必要的持久化
- 按需写入

**缺点:**
- 第一个边界前的工作不可恢复
- 复杂的状态转换
- 不清楚的持久化契约

7. **向后兼容** - 现有 SuspensionCheckpoint 可以读取为泛化模型
8. **公共 API 最小** - 主要是内部泛化

## 18. 最终决策

### 18.1 中心架构问题答案

**问题:**
> 如何让 Arctra 支持 DURABLE 非 HITL 自动执行，
> 通过最小化泛化现有 M5/M6 suspension/resume 模型实现，
> 同时保留现有的 EPHEMERAL ALLOW 快速路径？

**答案:**

## ✅ CONDITIONAL GO: 通过最小泛化现有持久化继续脊柱实现双模式执行

### 18.2 关键决策

**1. 分离三个正交关注点**
- ✅ 治理 (ALLOW / REQUIRE_APPROVAL / REJECT)
- ✅ 持久性 (EPHEMERAL / DURABLE)
- ✅ 继续倾向 (RUNNABLE / WAITING / COMPLETED)

**2. 持久性选择权威**
- ✅ AgentExecutionContext.withDurability()
- ✅ EPHEMERAL 是默认的
- ✅ REQUIRE_APPROVAL 自动升级到 DURABLE

**3. 第一个持久化边界**
- ✅ TOOL_BATCH_MATERIALIZED
- ✅ operationId 在物理调用前持久化
- ✅ T5 恢复语义完全重用

**4. 当前状态权威**
- ✅ CheckpointStore (单一)
- ✅ SuspensionCheckpoint (重新解释为持久化继续)
- ✅ checkpointVersion (单一 CAS)

**5. CHECK A/B 泛化**
- ✅ 已经是通用的
- ✅ 无需修改

**6. T5 组合**
- ✅ InvocationStateStore 重用
- ✅ InvocationRecoveryClassifier 重用
- ✅ operationId 保持稳定

**7. 继续触发器**
- ✅ 批准继续: resumeProcess(…, signal)
- ✅ 自动继续: resumeDurableProcess(…) (新)
- ✅ 收敛到单一内部管道

**8. EPHEMERAL 快速路径**
- ✅ 完全保留
- ✅ 零持久化开销

### 18.3 主要架构选择

**RESULT:** GO — 双模式执行通过最小泛化现有持久化继续脊柱

**理由:**

1. ✅ **单一恢复脊柱** - 满足 T6.2 统一约束
2. ✅ **87.5% 已经通用** - 最小化变更
3. ✅ **两个真实用例** - 不再"只有一个"
4. ✅ **EPHEMERAL 保留** - 快速路径不受影响
5. ✅ **T5 完整重用** - 物理尝试恢复
6. ✅ **CHECK A/B 重用** - 无重复 CAS
7. ✅ **向后兼容** - 遗留 checkpoint 可读
8. ✅ **公共 API 最小** - 主要内部泛化
