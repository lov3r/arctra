**任务目标:**

对抗性验证 M6-T6 NO-GO 决策背后的关键假设：

**验证方法:**

**核心发现:**

❌ **原始假设被证伪**

M6-T6 声称：
> "从头重新执行是安全的，因为工具恢复由 InvocationStateStore 处理"

**源代码真相:**
- ALLOW 执行**从不**创建 processId
- ALLOW 执行**从不**生成 operationId
- ALLOW 执行**从不**调用 InvocationStateStore
- ALLOW 执行**绕过**所有 Arctra 持久化机制

**但 M6-T6 NO-GO 仍然有效，原因已更新:**

原有理由（不准确）:
> "工具恢复由 InvocationStateStore 处理"

新理由（准确）:
> "普通执行是故意临时的。Checkpoint-backed 执行是持久化的。这是正确的设计选择，反映了自然的持久性边界（批准决策点）。"

### 6. 持久性契约分类 ✅

**经过源代码验证，Arctra 实际契约是:**

```
CONTRACT B — CHECKPOINT-BOUNDED DURABILITY

execute() = 临时执行（除非暂停物化）
resumeProcess() = checkpoint-backed 持久化执行

外部副作用责任:
- ALLOW 路径: 应用程序
- HITL 路径: Arctra (T5 分类)
```

**不是 CONTRACT A（完全持久化执行）**  
**不是 CONTRACT C（混合）**

## 关键发现

### 发现 #1: ALLOW 执行没有持久化状态

**源代码证据:**
- `processId` 仅在 Line 414 生成（`suspendForApprovalDurable()`）
- `operationId` 仅在 Line 425 生成（构建 `PendingToolCall`）
- `InvocationStateStore.recordInvocationIntent()` 仅在恢复路径调用

**ALLOW 执行路径完全绕过这些。**

### 发现 #2: M6-T6 声明不准确

**M6-T6 原始声明:**
> "InvocationStateStore prevents duplicate external side effects"

**源代码真相:**
> "InvocationStateStore prevents duplicate side effects **仅在 checkpoint-backed 恢复路径中**"

**ALLOW 路径从不使用 InvocationStateStore。**

### 发现 #3: 持久性边界是故意的

**这不是架构疏忽，而是正确的设计选择:**

**为什么批准是自然的 checkpoint 边界:**
- 人工决策点（自然异步）
- 操作批次已物化（稳定身份）
- 语义上有意义的暂停（非任意）
- 清晰的继续语义

**为什么 ALLOW 不需要 checkpoint:**
- 从头重新执行不会丢失决策（无人工批准）
- Checkpoint 写入开销不适用于所有执行
- 应用程序可以选择使用 HITL（如果需要持久性）

### 发现 #4: 文档需要澄清，而非架构需要修复

**需要的不是:**
- ❌ 通用执行 checkpoint
- ❌ ALLOW 路径 InvocationStateStore
- ❌ 新的持久化机制

**需要的是:**
- ✅ 明确的持久性契约文档
- ✅ API 文档澄清
- ✅ 外部副作用责任说明

## 最终决策

### ✅ RESULT B — CONDITIONAL GO: M6 持久性契约是 CHECKPOINT-BOUNDED

**含义:**

1. **普通 ALLOW 执行是故意临时的**

   - Checkpoint 开销不适用于所有执行
   - 批准是自然的持久性边界

2. **Checkpoint-backed 执行是持久化的**
   - 完整的恢复权威
   - T5 分类和解析
   - 跨 JVM 边界安全

3. **文档/API 契约必须明确说明这一点**

   - 需要说明外部副作用责任

4. **无需实施通用 checkpoint**
   - 当前设计是正确的
   - 不是架构疏忽
   - 临时性是可接受的权衡
